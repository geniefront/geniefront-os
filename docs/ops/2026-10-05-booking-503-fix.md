# Booking 503: isolate voice availability snapshots

Later on October 5, the user authorized the full workspace release. The complete
fix is now deployed to both production hosts; see [release verification](2026-10-05-full-production-release.md).
The implementation-only boundary below records the earlier checkpoint.

## Incident and evidence

On October 5, 2026, the public booking API intermittently returned Caddy's
`503 / no upstreams available`. On gf-b at 11:18:44–11:18:56 America/New_York,
the Node process logged no incoming requests; at 11:18:57 it processed 390
queued requests and completed a voice seven-day snapshot refresh (13,672 ms).
Caddy's five-second health check had timed out during that calculation.
Similar refresh/health-check failures occurred on gf-a.

The snapshot worker and cold-cache fallback previously computed seven days of
availability on the HTTP API's event loop. The inner slot/staff loops repeatedly
constructed Intl formatters and converted identical shift boundaries.

## Changes

- Cache a bounded set of Intl formatting rules by timezone. Cache wall-minute
  timestamps only within one request/snapshot, keyed by date, timezone and minute.
  Return new Date instances so callers cannot corrupt cached timestamps.
- Prepare staff/resource/existing-booking intervals outside the slot loop.
  Preserve DST conversion, closing periods, staff eligibility and live capacity checks.
- Compute date/service choices sequentially, yielding to the event loop between
  choices. Preload the catalog/roster once per seven-day refresh.
- Move periodic snapshots to `voice-snapshots.mjs`, a separate process/container.
  One tenant is calculated at a time, using the existing database leases. Compose
  limits this process to 0.5 CPU, 512 MiB and two DB connections; it exposes no host port.
- HTTP cold-cache reads and TeXML prewarming enqueue refreshes only. A missing,
  wrong-scope, wrong-day or expired snapshot returns a retryable `context_refreshing`
  error with a five-second retry hint. No HTTP fallback runs the seven-day calculation.
- Retain the existing five-minute maximum usable age, revision invalidation,
  lease expiry/ownership and failure backoff. Enqueueing does not clear a lease,
  replace a payload or bypass backoff. Final booking submissions still revalidate.
- Public booking GETs time out after five seconds per attempt, with at most three
  attempts and 500/1500 ms backoffs for network failures or 502/503/504. Body reads
  are also bounded. POSTs are never automatically retried. Bodyless GETs omit JSON
  Content-Type, avoiding an unnecessary preflight on initial shop resolution.
- Log API/worker event-loop P99/max delay and utilization every 30 seconds;
  warn above 250 ms. The worker reports scheduler progress through its private
  `/health`. Deployment health gating requires both API and worker to be healthy.

No schema migration is required. Existing business records are not rewritten.
In normal operation the worker continues maintaining the existing snapshot and
expiring voice reference tables, just as the old inline worker did.

## Local development

Run the API normally and run the snapshot process separately against the same
local environment:

```sh
bash scripts/run-env.sh local pnpm --filter @gf/api dev:snapshots
```

Without this process, cold initial voice contexts correctly remain retryable;
the API must not silently restore inline calculation.

## Verification

Database-free regressions:

```sh
pnpm --filter @gf/api exec vitest run --config vitest.booking-performance.config.ts
pnpm --filter @gf/scheduling test
pnpm --filter @gf/booking exec vitest run src/lib/api.test.ts src/pages/BookingExperiencePage.test.tsx src/pages/BookPage.test.tsx src/pages/ManageBookingPage.test.tsx
```

Full isolated regression and process isolation check:

```sh
node scripts/test-booking-performance.mjs
```

This command creates its own uniquely named PostgreSQL container on an ephemeral
loopback port. It never reads `.env` or accepts an external database URL. It loads
fixtures and runs booking/voice tests only there, with captured communications,
then removes its own container/volume. Do not replace it with unqualified API
integration tests against a developer or hosted database.

Verified locally:

- 19 snapshot/availability unit regressions, 115 scheduling tests, and 47 booking
  client/page tests passed.
- 118 isolated PostgreSQL public-booking/voice integration tests passed, including
  lease competition, expired owner rejection, invalidation during refresh, cold
  enqueue, retained backoff, and live booking conflict validation.
- Both entrypoints bundle. The API bundle contains neither snapshot scheduler nor
  refresh executor; the worker bundle contains both.
- The real standalone worker published a snapshot against the disposable DB.
  With its thread deliberately blocked for six seconds by a test-only preload,
  30 real API HTTP reads (health/shop/services) all returned 200, P95/max 27 ms.
- A seven-day/ten-service/four-staff local fixture completed in 57–101 ms while
  timers continued to run. This is a local benchmark, not a production latency claim.
- API/booking/scheduling type checks, Compose configuration and repository guards passed.

## Release boundaries

At implementation verification, no production deployment, database mutation,
cache purge, service restart or test booking was performed. The workspace also
contains unrelated uncommitted commerce work; do not deploy the whole working tree
as this hotfix. Prepare a release based on the actual deployed revision with only
the scheduling, snapshot isolation, client retry and required packaging changes.

Ship the new worker artifact and service together with the API that removes the
inline scheduler. Roll one host at a time and require both health checks before
continuing. Inspect event-loop delay, refresh duration/age and 503 logs over multiple
refresh cycles. Production validation uses GETs only; no test bookings or migrations.

Rollback uses the prior API image/Compose as a matched set (old API owns its inline
worker); stop the standalone service when restoring the old arrangement. Existing
lease expiry permits recovery after an interrupted worker without clearing leases
or modifying appointments.
