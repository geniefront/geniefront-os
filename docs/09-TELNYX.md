## 1. 动手之前必须先知道的三件事 ⚠️

### 1.1 换 CSP，10DLC 要**重新排队**

10DLC 的 brand 与 campaign 注册在 **TCR（The Campaign Registry）**，
但**由 CSP 代为提交** —— Twilio 是一个 CSP，Telnyx 是另一个。
换供应商不是"把号码搬过去"，是**在新 CSP 名下重新注册 campaign**，
审核队列从头开始。

**所以：在 Telnyx 的 10DLC 批下来之前，不要注销 Twilio 那边正在审的申请。**
两边并行的成本几乎为零（没批准就不产生 campaign 月费），
而"两边都没有"是唯一真正会让 Phase 2.5 卡死的状态。

> 需要在 Telnyx 开户后确认的一件事：**brand 能不能沿用**（把已有 TCR brand 关联过来），
> 还是必须连 brand 一起重注册。能沿用就省掉几天到一两周。
> 这个答案只能问 Telnyx 支持，文档上写得不清楚。

### 1.2 短信仍然不进任何依赖链

`03` 决策 11 与宪法第 13 条**原样有效**，只是把"等 Twilio A2P"换成"等 Telnyx A2P"：

- 门店数 ≥ 10 家 **且** 10DLC 批准，才启动 Phase 2.5
- 在那之前，代码里**不写任何短信依赖**：通知走邮件 / Web Magic Link /
  页面实时通知 / 前台人工回呼
- 手机号 OTP 登录同样等这条通道（`01` §5）

换供应商这件事本身，不改变上面任何一条。

### 1.3 AI 电话换的是**两层**，不是一层

原方案是两个供应商叠起来的：

```
Twilio（号码 + 语音信道） ← Vapi（对话编排：ASR + LLM + TTS + 打断处理）
```

Telnyx 两层都能自己出：

```
Telnyx（号码 + 语音信道 + AI Assistant 对话编排）
```

**好处**：少一个供应商、少一层网络跳转（延迟）、一份账单、一套 webhook 签名。
**代价**：编排层从"可换的第三方"变成"和承载通道绑定的自家产品" ——
Vapi 不好用可以换 Retell/Bland 而保留 Twilio 号码，Telnyx 的 assistant 不好用就得整个换。

> ⚠️ **这一条决定了 §7 的任务顺序**：先花半天做**口音实测**（§4.3），
> 再决定要不要把号码全部搬过去。搬完再发现听不懂粤语，代价大得多。

## 2. 产品映射：原方案 → Telnyx

| 原方案 | Telnyx 上对应 | 备注 |

| Twilio Messaging + A2P | **Telnyx Messaging + 10DLC 注册** | Phase 2.5 才用 |

- LLM 供应商仍是 **Anthropic**（`03` 决策 22）。Telnyx 的 assistant 若能配置外部模型就用
  Claude；若只能用它自带的推理，那也只是**电话这一条路**上的模型，
  前台副驾、价目表视觉提取、开店向导**全部仍走 Anthropic**，不受影响。
- `usage_events` 的四种计量（`ai_assist` / `ai_call_min` / `sms` / `email`）**不变**。
  换供应商不改计量口径，只改单价（`04` §4.1）。
- 「AI 只能从排期引擎返回的真实空档里选，不许自己算时间」——
  这条护栏与供应商无关，照旧（`04` §5）。

## 3. 架构影响：几乎没有 ⭐

这是选 Telnyx 相对省心的地方 —— 它落在**已经存在的那条边界**上：

```
Telnyx（号码 · 语音 · AI Assistant · 短信）
        │  webhook（Ed25519 签名）
        ▼
   Fastify 无状态实例  ──►  命令总线  ──►  Postgres
        ▲                      │
        └── AI Assistant tool ─┘   （只读快照 + 建预约草案）
```

- **不需要 VPS 长连接、不需要自建媒体流**（宪法第 10 条）：
  媒体在 Telnyx 侧终结，我们只收 webhook。这一点与原方案一致，是当初选 Vapi 的同一个理由。
- **不需要新的状态层**：通话产生的东西最终只落成
  `appointments(source='phone_ai')` 草案 + `usage_events(kind='ai_call_min')`。
- **两台实例零协调**：webhook 打到任意一台都一样，因为它只是又一个写命令的入口。

**需要新增的只有一件**：webhook 的**签名验证中间件**。

> ⚠️ 这是整条链路上唯一的安全要害。没有签名验证，任何人都能 POST 一条
> "客人预约了明天三点" 进你的复核队列 —— 甚至更糟，触发计费事件。
> Telnyx 用 **Ed25519** 签名（请求头带签名与时间戳，配对控制台里的 public key）。
> 验证要点：**先验签再解析 body**、**校验时间戳窗口防重放**、
> **public key 从环境变量读且不同环境不同 key**。

## 4. AI 电话：落地方式

### 4.1 目标没变：三要素提取

`03` 决策 6 原样有效 —— AI 电话**不是**全自动前台，它只干一件事：

> 从来电里提取 **项目 + 技师偏好 + 期望时间**（来电号码自带），
> 匹配排期引擎给出的**真实空档**，生成 `source=phone_ai` 的预约草案，
> **直推前台 1 秒复核队列**。

任何"AI 直接确认预约不用人看"的想法，在门店数 < 100 之前都不要碰。

### 4.2 三要素怎么拿回来

给 assistant 配三个 **tool**，全部指向我们自己的接口（都要签名验证）：

| tool | 方向 | 作用 |
| :--- | :--- | :--- |
| `lookup_customer` | 只读 | 用来电号码查老客：姓名、上次做什么、常指定谁。**同号多客户时返回列表让 AI 问"请问是哪位"**（决策 21，不许自动挑一个） |
| `find_slots` | 只读 | 传项目 + 期望时间窗，**由排期引擎返回真实空档**。AI 只能从这个列表里报时间 |
| `draft_appointment` | 写 | 走命令总线建 `source=phone_ai` 草案。**必须带幂等键**（通话重连会重放） |

**为什么不让 assistant 直接写库**：它写的每一条都要过权限、幂等、审计（宪法第 1 条）。
tool 打到命令总线是唯一一条路，AI 和 UI 走的是同一条 —— 这条不为任何供应商破例。

### 4.3 ⭐ 先做口音实测，再决定搬不搬号码

这是 §7 任务清单里**第一条**的原因。测试集要覆盖真实客群（`00` §2）：

| 场景 | 通过标准 |
| :--- | :--- |
| 带口音的英语（华人 / 越南裔 / 西语裔） | 三要素提取正确率 ≥ 80%，错的那些**不能是静默错误**（宁可转人工） |
| 粤语 / 普通话夹杂英文项目名（"我要做 gel 甲"） | 至少能听懂项目并转人工，不能挂断 |
| 越南语 | 同上 |
| 嘈杂背景（店里放音乐、吹风机） | 不误触发、不乱打断 |
| 说到一半改主意（"五点……算了六点吧"） | 不能解析成 06:00 —— 这正是当初否掉 DeepSeek 的那个坑（决策 22） |
| 明确要求转人工 | 100% 转接或留言，**永不挂断** |

**不通过怎么办**：保留 Twilio + Vapi 跑 AI 电话，**只把短信搬到 Telnyx**。
两件事本来就可以分开搬 —— 这也是为什么 §7 把它们排成两条独立的线。

> ✅ **换供应商的代价已经被压到很小了**（2026-08-16）。
> 我们这一侧的三个 tool 接口和验签是**按 Telnyx 的 webhook 格式**写的，
> 但接口本身与供应商无关（收 `to` / `from` / 听到的三要素，返回真实空档）。
> 回退到 Vapi 只要换掉 `apps/api/src/telnyx/` 里的验签方式和字段名映射，
> `call_drafts`、命令、复核界面、排期引擎**一行都不用动**。
>
> ⬜ **实测结果写在这里**（A3 做完后填）：
>
> | 场景 | 通过 / 不通过 | 备注 |
> | :--- | :--- | :--- |
> | 带口音的英语 | | |
> | 粤语 / 普通话夹英文项目名 | | |
> | 越南语 | | |
> | 嘈杂背景 | | |
> | 说到一半改主意（「五点……算了六点吧」） | | |
> | 明确要求转人工 | | |

### 4.4 录音与合规（不因换供应商而改变）

- **加州、宾州等 two-party consent 州**：录音必须开场告知。
  做成模板化开场白 + 按州自动启用（`04` §5）。
- 通话录音属于个人信息：存储位置、保留期、访问留痕都按 `02` §15 的口径。
- ToS 里的免责条款照旧："系统为辅助工具，不构成法定记录"（`03` §C4）。

#### A2 要在 Telnyx 控制台里配的三个 tool

全部 `POST`，全部要开 webhook 签名。`{to}` 是被叫号码（我们靠它定位门店）：

| tool | URL | 传什么 |
| :--- | :--- | :--- |
| `lookup_customer` | `/v1/telnyx/tools/lookup_customer` | `to`, `from` |
| `find_slots` | `/v1/telnyx/tools/find_slots` | `to`, `duration_min`, `around`(ISO), `staff_membership_id?` |
| `draft_appointment` | `/v1/telnyx/tools/draft_appointment` | `to`, `from`, `call_session_id`, `service_heard`, `staff_heard`, `time_heard`, `slot_starts_at`, `duration_min`, `caller_name`, `confidence_bp`, `notes` |

通话事件 webhook：`/v1/telnyx/webhook`（只处理 `call.hangup`，用来记分钟数）。

> 三个接口的返回里都带一句 `guidance` —— 那是**直接写给模型看的约束**
> （「只能从下面这些时间里选」「这个号码下有多位客人，请问清是哪一位」）。
> 放在返回里比藏在 system prompt 里可靠：它跟着数据一起到，而且换 assistant 不会丢。

#### 这一期实现里几条与文档不同的决定

| 文档原本设想 | 实际做法 | 为什么 |
| :--- | :--- | :--- |
| AI 建 `appointments(source='phone_ai')` 草案 | AI 只写 **`call_drafts`** 队列，**完全不碰 appointments** | AI 建的东西会**占住日程表上的位置**：一通没听清的电话就能把周六下午卡掉一格。改成独立队列之后，就算验签整个被绕过，攻击者也只能往待办里塞垃圾 |
| — | AI 的权限只有 `call.draft` 一条 | webhook 是**没有 Bearer token** 的入口。给它 `appointment.write` 等于把排期表的写权限挂在一个环境变量上 |
| — | AI 报的时间**服务端再验一遍** | 模型很擅长说出一个听起来合理、但那天店里没人在班的时间。对不上就清空时间、标低置信度、把原话留着（`assertRealSlot`） |
| — | 每个要素同时存「听到的原话」和「匹配到的 id」 | 只存匹配结果的话前台没法核对 —— 屏幕上写着 `Gel Manicure`，而客人说的是 `gel removal`，价格差一倍 |
| — | 名字匹配**只认完全相等或包含**，不做编辑距离 | `gel manicure` 和 `gel removal` 的编辑距离很近。宁可匹配不上让前台填，也不要匹配错让前台以为填对了 |
