# 前端反馈状态审查：加载 / 成功 / 失败与重复提交（2026-09-11）

范围：`apps/web`。不涉及 geniefront-v2，未修改后端、数据库或业务契约，未部署。

用户反馈的现象是「有时候不知道在 loading，也不知道成了还是败了」。审查下来，
根因不在各个页面，而在**共享按钮组件根本没有可见的进行中状态**——页面已经
老老实实把 `isPending` 传下去了，只是传下去之后什么也没发生。

## 一、根因：`isPending` 传了等于没传

HeroUI v3 的 `Button` 接受 `isPending`，但它在样式表里对应的
`status-pending` 规则**全文只有一条 `pointer-events: none`**：

```css
@utility status-pending { @apply pointer-events-none; }
```

不转圈、不变暗、外观零变化，只是突然点不动了。全站已有 22 处按钮传了
`isPending`，用户看到的却是「按钮好像卡住了」——与故障无法区分，于是继续点。

修复落在适配层 `components/ui/Button.tsx`：进行中显示转圈 + 变暗 + 光标变
`progress`；图标按钮的图标本身换成转圈，避免挤爆固定尺寸。

一处认知修正值得记下来：HeroUI 原生的 `isPending` **拦截是完整的**——它置
`aria-disabled`，指针与键盘的 press 一律不再触发 `onPress`，同时保留
`tabindex` 让焦点不丢。因此不要顺手把 `isPending` 并进 `isDisabled`：
`disabled` 会把按钮移出 Tab 序列，用户刚按下的那个按钮在焦点还停在上面时
突然不可聚焦，键盘用户当场失去位置。初版实现犯了这个错，已改回并加测试锁住。

## 二、二次确认弹窗按一次还是按三次，此前没人管

`ui/Modal` 的 `ConfirmDialog` 守着的全是不可逆操作（作废单据、退款、删除员工、
批量删除通知）。按下确认到 `onConfirm` 兑现之间，按钮外观毫无变化也不拦第二次
按下——网络稍慢，前台再点一次就是第二笔退款。

现在弹窗自带进行中状态：确认键转圈并锁住、取消键一并锁住（免得中途关掉丢状态）、
兑现后自行关闭、失败留在原地让 toast 有处可依。`runningRef` 与 `running` 两者
都要：状态更新要等下一次渲染，而连续两次点击可能落在同一批里，ref 是同步的。

`pages/Notifications.tsx` 的批量操作原本**先关弹窗再跑**，几十个请求在界面上
毫无痕迹；改为交给弹窗托管，过程可见。

## 三、60 处「灰掉但不转圈」的提交键

全站另有 60 处写成 `disabled={xxxMutation.isPending}`：拦是拦住了，但用户看到的
只是按钮变灰，同样分不清「在处理」还是「坏了」。统一补上 `isPending`，覆盖
收银、日结、营销（次卡核销 / 优惠券 / 礼品卡 / 积分）、客户、工单作废与退款、
轮牌、设置、技师端打卡与开始/完成服务等。

判定与改写由脚本完成，规则是：该按钮的 `onPress`/`onClick` 直接触发写操作
（`mutateAsync` / `mutate` / `runCommand`），且其 `disabled` 表达式里含进行中项。
取消键不在此列——已逐个核对，确认没有误伤。

## 四、15 处完全没有进行中状态的按钮

| 位置 | 风险 | 处理 |
|---|---|---|
| `Rooms` 房态卡的转打扫 / 打扫完成 / 恢复空闲 / 停用检修（含两处状态下拉） | 前台一天里按得最多，连点即连发切态命令 | 新增 `busyRoomId` **按房间粒度**记录：切 A 房时 B 房不受影响；原生 `<button>` 一并补转圈与禁用样式 |
| `Customers` 发送短信 | 按条计费且无法撤回 | 绑 `sendSmsMutation.isPending` |
| `HealthForms` AI 生成（含一排快捷提示词） | 耗时数秒、按次计费 | 补 `isPending` + `aiGeneratingRef` 同步防重 |
| `CreateAppointmentModal` 冲突后的「强制排入」 | 会真的创建预约，连点即重复预约 | 此前按下即关弹窗再异步提交，中间无转圈无拦截；改为保持弹窗、按钮转圈 |
| `Settings` 移除授权域名 | —— | 按行记录 `removingOriginId`，避免整列「移除」一起灰掉 |
| `CatalogPresetPicker` 批量添加预设 | 串行写多条 | `isDisabled` 拆成 `isPending` + 选中数判定 |

唯一保留未改的是 `Notifications` 里点击通知跳转的那个按钮：它 mark-read 之后
立刻导航离开，导航本身就是反馈，给一个马上要卸载的按钮加转圈没有意义。

## 五、「加载失败」长得和「暂无数据」一模一样

这是第二类「不知道成没成」：请求挂掉时页面落到空状态上，用户据此认定店里今天
没有通知、门店没有套餐、从未同步过口碑——然后按错误的前提继续操作。

新增 `ui/QueryState` 的 `SectionError`（区块级失败，红色 + 说明 + 重试，与空状态
明确区分），并接入：

- `Notifications` 通知列表——失败不再显示「暂无通知」
- `BillingPanel` 订阅信息与账单列表
- `BundleManagerPanel` 套餐目录——失败不再显示「暂无组合套餐」
- `ReviewSourcesPanel` 同步记录
- `WalkInBundleModal` 套餐选择器——失败不再显示「本店暂无组合套餐」
- `Profile` 整页补 `PageError`：此前失败会渲染成一张空白表单，用户会当成资料
  真的是空的，填完再保存

## 六、新增的公共设施

`lib/asyncAction.ts` 的 `useAsyncAction`：把「同步防重 + 进行中 + 成功提示 +
失败提示」收敛成一次调用，供后续新写的写操作直接使用。

```tsx
const save = useAsyncAction(async () => { await saveMutation.mutateAsync(input); },
                           { success: t('saved') });
<GuardedButton permission="…" isPending={save.isRunning} onPress={save.run}>保存</GuardedButton>
```

⚠️ 它存在的理由不只是省字：一个处理函数常常串起多个 mutation（先开单再开始
计时），任何单个 `mutation.isPending` 都只覆盖其中一段，段与段之间按钮会短暂
恢复可点。

## 八、表单校验：从「只弹 toast」落到字段上

这是第三类「不知道成没成」：校验不通过时**只弹一条 toast**。toast 几秒后消失、
不指明是哪一格、对读屏用户等同于一段与表单无关的播报。设置页的项目编辑有十几个
字段，用户读完「项目名称不能为空」还得自己去找是哪个名称 —— 而门店 iPad 上多数
字段并不在当前视口里。

全站 37 处必填校验属于这种写法，其中 30 处已落到字段上：

- `components/ui/Input` 新增 `error` 属性：红框 + `aria-invalid` +
  `aria-describedby` 指向字段下方的错误文案。
- `lib/formFeedback` 的 `useFieldErrors`：记错误、移焦点、滚到视口中央，
  并在用户开始修改时自动消红。
- **toast 改为按需补位**：字段就在眼前时不再弹（同一句话说两遍是噪音），
  字段在折叠面板、另一个标签页或滚动区域之外时才弹 —— 那时红框不可见，
  只有 toast 能说明「提交没有发生，以及为什么」。取不到元素尺寸时一律按
  「看不见」处理，宁可多说一句。

已接入：登录、重设密码、激活、顾客档案（页面与抽屉各一处）、员工档案、
个人资料、房间/工位、项目与分类、组合套餐、次卡/发售/优惠券、新建短信、
日结差异说明、新建预约、开店向导三步、图片 URL、完工加项。

`CreateAppointmentModal` 原本手写过一份同样的逻辑（`nameError` 布尔 + 红框 +
文案），已合并到共享 hook，顺带获得聚焦与滚动。

仍保留纯 toast 的 7 处，是有意为之：`BillingPanel` 那两处不是字段校验，而是
「服务端没返回 URL」；`Queue` 的三处追加项目校验，其提交键本就按
`serviceId && staffId` 禁用着，属于防御性兜底；另有一处是一组勾选框而非单一
输入框，没有可聚焦的落点。

## 九、乐观更新：只在够安全的地方用

乐观更新的三个前提缺一不可 —— **幂等、无金额且不可见于顾客、失败可无声回滚**。
据此只对两处启用：通知的「标记已读」与「全部已读」。点下去红点立刻消失，失败则
把本地快照原样放回，用户看到的就是「没点上」。

明确不做的：删除（不可逆，先抹掉再变回来会让用户以为自己删错了）、以及全部业务
命令 —— 开单、结账、退款「看起来成功了」与「真的成功了」的差别，前台要到日结
对不上账时才发现。

同时处理了另一种体感问题：**翻页时整屏清空**。

- 日程按前后一天翻页时保留上一天的内容，不再闪白屏。但旧数据属于**另一个营业
  日**，会被误读成经营事实，因此配了一层遮罩：说明正在切换、挡住这期间的所有
  点击。遮罩必须够厚 —— 旧日历上每一列都写着「暂无预约」，那行字在切换期间是
  错的。
- 通知切换分类标签时同样保留上一组结果。这里不需要遮罩：通知列表不承载「当前
  正在操作哪一单」这类会被误读的上下文。

## 十、顺带修掉的一处测试基建缺陷

`lib/toast.ts` 在模块加载期直接读 `toastQueue.add`。Vitest 的模块替身在**读取**
未声明的导出时就会抛错，因此任何 mock 了 `@heroui/react` 的测试，只要其被测组件
间接引用到 toast，整个测试文件就会以一条与被测行为毫不相干的错误失败。改为
try/catch：没有队列可改并不是错误，保持默认时长即可。

## 十一、格式校验：从「静默纠正」改成「判定」

第八节统一的是「错误往哪里放」，这一节统一「怎么判对错」。原先这一半散落在各页
的行内正则里，同一件事有好几种写法，而且**多数写法不是判定，是静默纠正**：

| 原写法 | 用户打错字时实际发生的事 |
|---|---|
| `dollarsToCents(servicePrice)` | 项目以 **$0.00** 上架，界面不提示任何异常 |
| `parseInt(serviceDuration) \|\| 30` | 时长静默变成 30 分钟 |
| `Math.round(parseFloat(cpnValue) * 100)` | 折扣券把 **NaN** 提交给服务端 |
| 技师端小费正则不过就 `return` | 按钮点了毫无反应，连提示都没有 |

`dollarsToCents` 本身没有错 —— 它是给结账流程写的宽容解析器，把非数字剔掉再算
是那个场景的正确行为。错在拿它去当输入框的校验。

新增 `lib/validation.ts`：`parseMoney` / `parseDurationMinutes` / `parseEmail` /
`parsePin` / `parseCount`，**一律返回判定结果而不是纠正后的值**，失败带可区分的
`reason`。纯函数、不碰 i18n 与 DOM，因此可以被纯函数测试完全覆盖；`reason` 到母语
文案的映射单独放在 `lib/validationMessage.ts`，文案写成可执行句式（「金额只能填
数字，最多两位小数，例如 45 或 45.50」而不是「格式不正确」）。

已接入：目录项目的价格与时长、次卡价格、优惠券面额与门槛、礼品卡面额与售价、
技师端现金小费、开店向导的项目录入、登录邮箱、门店 PIN。预约弹窗里原有的
`parseDuration` 也并了进来 —— 它的边界（1 分钟）与目录项目（5 分钟）不同，因此
下限由调用方给出，规则层不写死。

测试里有一条特意写的等价断言：对**合法**输入，`parseMoney` 与既有的
`dollarsToCents` 结果必须逐个相同；差别只在于前者会对非法输入说「不」。这保证
收紧校验没有顺带改动任何一笔正常金额的算法。

## 十二、骨架屏

居中转圈只说明「在加载」，骨架屏还说明**将要出现什么**：结构提前占位，数据到达
时内容落进已有的格子里，而不是把整块界面重排一遍。对门店 iPad 的实际意义是少一次
视觉跳动 —— 前台的手指往往已经停在她预期按钮出现的位置上。

`PageLoading` 新增 `layout` 属性，21 处首屏加载按各自真实版式接入：
`board`（看板）、`calendar`（日程）、`list`（客户/单据/消息/收银）、
`table`（经营数据/薪资/通信记录/员工/通话）、`cards`（房态/营销/仪表盘/轮牌）、
`detail`（设置/个人资料/网站装修/硬件/日结）。

⚠️ **形状必须与真实版式对齐。** 首版骨架漏掉了页头与工具条，数据到达时整块内容
仍会被真实页头往下顶一截 —— 那正是骨架屏本该消除的跳动。补上共用的页头、工具条
与指标条之后，房态页的骨架与真实版式逐块对得上。形状对不上的骨架比转圈更糟：
它承诺了一个并不会出现的版式，数据到达时照样重排，中间还多骗了用户一次。

骨架整块 `aria-hidden`（它没有内容），另起一行可读的状态文案说明正在加载哪一块
数据 —— 转圈版本原本就有这句话，换成骨架屏不能把它丢掉，测试锁住了这一点。

## 十三、未覆盖

- 仅以 `front_desk` 角色走查；`owner` 才可见的经营数据、薪资、平台后台未逐页核对。
- 校验只覆盖「当场可见的手误」。邮箱是否真实存在、电话号码是否可达，仍要等发信
  或发短信才知道，这不是前端能判定的。
- 骨架屏只接了首屏加载。局部区块（抽屉、弹窗内的列表）仍是转圈，它们体量小、
  出现时长短，暂未改动。
