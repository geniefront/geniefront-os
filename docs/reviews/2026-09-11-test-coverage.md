## 但「覆盖率低」不是这里的正确结论

真正需要判断的是**未覆盖的是哪一类代码**。查下来：

- **可抽取的逻辑已经测得很好**：`checkoutMath`、`cashCount`、`kanbanMetrics`、
  `commission`、`split`、`timeline`、`assignment`… 都在 `features/*/` 下有纯函数测试，
  而且写得细（最大余额法那组测试连负数冲账都断言了）
- **页面里剩下的主要是接线** —— 把 hook 接到按钮上、把状态接到弹窗上

而这次审查挖出的问题，**几乎全部是接线问题**：

| 问题 | 类别 |
|---|---|
| 命令定义了没注册 → 404 | 接线 |
| 打折/超容量的权限没判 | 接线 |
| 19 处按钮没门禁 | 接线 |
| 幂等键在提交时才生成 | 接线 |
| 21 个文案 key 不存在 | 接线 |
| 客户搜索没传给服务端 | 接线 |
| 上传的是原文件不是压缩后的 | 接线 |

这些**没有一个**会被「给页面加一个渲染测试」抓到，
但每一个都会被一条针对该类别的静态检查抓到 —— 而且是全站一次抓完。

## 因此这一轮选的是护栏，不是页面测试

新增四个可重复运行的检查，全部接入 `scripts/lint-guards.sh`：

| 脚本 | 抓的是哪一类 |
|---|---|
| `check-permission-matrix.mjs` | 界面画的门 vs 服务端判的门；死权限 |
| `check-idempotency.mjs` | 幂等键随调用走而不是随意图走 |
| `check-money-parsing.mjs` | 钱路径上的静默纠正 |
| `check-i18n-keys.mjs` | 字典里不存在的文案 key |

加上五个新测试文件（24 条用例），测试总数 441 → **465**。

护栏比页面测试更适合这类问题的理由很直接：一条 `check-permission-matrix`
挡住的是「全站任何一个写入口漏了门禁」，而要用页面测试达到同样的覆盖，
得给 37 个页面的每一个写入口各写一条 —— 写不完，而且漏写的那一处
恰恰不会有人发现。

## 仍然建议补的页面测试（未做）

护栏挡不住「这一页的业务流程走不通」。三个页面值得各补一条**冒烟**测试
（渲染 + 走一遍主流程，不追求覆盖率）：

1. **`Queue.tsx`** —— 30 个写操作，是前台一整天都在看的那一页
2. **`DayClose.tsx`** —— 封账不可逆，且刚改过金额判定
3. **`Checkout.tsx`** —— 与排队页并行的第二套结账实现（见 [B 线](./2026-09-11-money-path.md) B-2）

没有在本轮做：给 2855 行的组件写测试，要么大量 mock（脆，改一行就红，
最后被人 skip 掉），要么起真实数据（慢，且要 DB）。做得不好的页面测试
比没有更糟 —— 它会消耗信任。这三条值得单独规划，**不适合在一轮审查的末尾赶出来。**
