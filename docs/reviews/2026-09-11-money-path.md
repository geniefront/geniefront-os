# B 线：钱路径数值口径

> 对账脚本：`scripts/check-money-parsing.mjs`（已接入 `lint-guards.sh` 第 12 条）

## 先说好的部分

服务端的钱层写得扎实，不需要动：

- **整数分贯穿全程**，没有浮点金额
- **`largestRemainderSplit`（最大余额法）是拆分的唯一实现**，注释写明了
  「返回值之和恒等于 total 是这个模块存在的全部理由」，负数分支单独处理
  以保证冲账金额与原单精确相反 —— 这一条想到了，说明写的人真的对过账
- **`ticket.pay` 不信客户端传来的 `taxCents`**，自己按门店设置重算，
  再与实收逐分比对，不等就 `PAYMENT_MISMATCH`

有了这道服务端比对，钱上的错不会静默发生 —— 它会变成一个结不了账的单。
下面三条问题正是这样暴露的。

---

## B-1 ⭐⭐ 内含税模式整条不能用

`taxCalculationMode: 'inclusive'` 在设置页里是个可选项，有说明文案
（`settings.stTaxModeDesc`：「内含税（标价已含税）」），服务端
`locationTaxCents` 也正确实现了拆税。但：

**① 前端根本没读这个设置。** `features/queue/checkoutMath.ts` 与
`pages/Checkout.tsx` 两处都一律按外加税算。

**② 服务端把拆出来的税又加了一遍。** `ticket.close` 的应收写成
`净额 + 税 + 小费 + 附加费`，而内含税下 `subtotalCents` **本身就含税**
（`tax.test.ts` 的断言写得很清楚：传入 10888、拆出税 888、净额 10000）。
于是应收变成 10888 + 888。`ticket.closeGroup` 里有同样的一份。

两个数不相等 → 内含税门店的**每一单都撞 `PAYMENT_MISMATCH`**。
功能在设置页里可选，实际一单也结不了。

好消息是它**响亮地坏**而不是静默地错 —— 服务端那道比对把它挡住了。

### 修法

抽出纯函数 `checkoutDueCents`（`apps/api/src/tax.ts`），把「两种税制下
`taxCents` 的含义不同」这件事写进一个地方：

```
外加税：应收 = 净额 + 税
内含税：应收 = 标价（税已在其中），taxCents 只是报给税务局的那一部分
```

`ticket.close` 与 `ticket.closeGroup` 都改为调用它。前端两处结账实现
同步实现内含税，并在测试里用**与服务端同一组数字**断言（10888 / 888），
这样两边一旦漂移，测试会先于门店发现。

**验证**：把前端的内含税分支强制关掉后复跑，4 条新用例里红 2 条。

## B-2 ⭐ 两套并行的结账实现，算出不同的刷卡附加费

`/checkout` 页（`pages/Checkout.tsx`）与排队页
（`features/queue/checkoutMath.ts`）各有一份完整的税费算法。两者对同一家店
给出不同的结果：

| | 附加费基数 |
|---|---|
| 排队页 | 服务应收（**不含小费**） |
| `/checkout` 页 | 服务应收 **+ 小费** |

排队页那份的注释写明了理由：「多数州禁止对小费部分加收刷卡手续费 ——
把小费算进基数是实打实的合规风险」。`/checkout` 页违反的正是这一条，
而且同一家店在两个界面结账会收到不同的附加费。

已修 `/checkout` 页的基数。但**根因是这两份实现不该并存** ——
这次是附加费基数与内含税，下次会是别的。建议把 `/checkout` 页改为调用
`computeCheckoutTotals`。没有在本轮做：那是一次需要端到端覆盖才敢动的重构，
而结账是全系统最不能出错的一条路。**留给单独一次有测试打底的改动。**

## B-3 ⭐ 宽容解析器被当验证器用（AUD-04）

上一轮修了目录价与时长，但同类写法还散在别处。共同形状是**静默纠正**：

| 写法 | 打错字时实际发生的事 |
|---|---|
| `parseFloat(taxRate) \|\| 0` | **营业税从此变成 0%**，界面提示保存成功 |
| `dollarsToCents(cashDrawerFloat)` | 备用金变 $0，此后每天的现金差额都不对 |
| `dollarsToCents(manualCountedStr)` | 盘点 807 打成 `8o7` → **$8.70**，日结的差额本身就算错了 |
| `parseInt(validDays, 10) \|\| 365` | 客人买到的次卡不是他看到的那张 |
| `parseInt(earnRate, 10) \|\| 100` | 积分兑换率回落默认值，店主以为改了 |
| `parseFloat(e.target.value) \|\| 0` | 提成比例：全选删掉准备重打的那一瞬间就变成 **0%** |

最后一条值得单独说：`EmployeePerformance` 的提成比例存的是**数字态**，
每一次按键都会被「纠正」一遍。把 45 全选删掉准备重打，那一刻状态已经是 0；
此时保存，这位技师的提成就是 0%。已改为存字符串、提交时判定。

### 护栏

`scripts/check-money-parsing.mjs` 按**赋值的字段名**判定（`*Cents`、`*Rate`、
`*Percent`、`*Price`、`Sessions`、`ValidDays`…），而不是「文件里出现过
parseInt」—— 纯 UI 步进器把 `parseInt(...) || 1` 夹在 `Math.max` 里是控件语义，
不是校验。

豁免分两级，每条写明理由：整文件豁免只给定义处与对照注释；收款行那两格用
**行级**豁免（边输边改的金额严格解析会在打到「5.」时判失败，对着收银台的人
是敌意行为；它由服务端应收比对兜底，且界面上「还差 $XX」当场可见）。
行级比整文件窄一档 —— 整文件豁免会把这个文件里**将来**写错的地方一起放过。

## B-4 复核通过：取整方向没有冲突

前端金额解析**截断**（宁少不多），服务端税额**四舍五入** —— 一度看起来是
口径不一致，实际不是同一个操作：

- 截断的是「用户敲进来的金额字符串 → 分」，多打的小数位不该替他进位
- 四舍五入的是「计算出来的乘积 → 分」，这是税务上的标准做法

两者不在同一条计算链上，没有冲突。**写下来是为了下次别再当成 bug 改一遍。**
