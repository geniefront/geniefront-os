# H 线：长列表与首屏

## H-1 ⭐⭐ 客户搜索只在取回来的那 200 行里做

这条本来是性能审查，结果挖到的是**功能缺陷**。

`Customers.tsx` 固定 `useCustomerList({ limit: 200 })`，然后在返回的 200 行里
做客户端模糊匹配。于是：

> **超过 200 位客人的店，第 201 位在搜索框里永远找不到。**

前台输了名字没结果，不会怀疑是分页问题，只会判定「系统里没有这个人」——
然后建一个重复档案。而重复档案会把这位客人的历史、次卡、积分一分为二。

更刺眼的是服务端**本来就支持**（`queries/customer.ts:285` 的 `q`），
而且契约注释写得很清楚：

> ⭐ 服务端**优先按手机后四位匹配** —— 前台在电话里问的第一句就是
> 「您手机后四位是多少」，而客人的全名她多半拼不出来（越南名、韩国名）。

这条能力从来没接上。数据层连 `placeholderData` 都为「逐字输入搜索词」准备好了，
唯独没人把 `q` 传进去。

**已修**：搜索词防抖 300ms 后传给服务端；客户端模糊匹配**保留**在上层 ——
它兜的是拼写错误，SQL 匹配兜不住。两层各司其职：服务端把候选集缩到对的那 200 行，
客户端在其中容错排序。

### 同源的第二个问题（未修）

顶部那排指标（VIP 数、30 天活跃、沉睡客户）也是在 `rawRows` 这 200 行里数的。
只有「共 N 位客人」用的是服务端的 `total`。

所以对超过 200 位客人的店，那几个数字的真实含义是「前 200 位里有几个 VIP」，
而界面上它看起来是全店口径。**没有在本轮修** —— 正确做法是服务端出聚合，
那要加接口，不是审查该顺手做的事。

## H-2 ⭐ 登录页就下载了 3.1 MB

实测（生产构建，`vite preview` + Playwright 统计真实响应体）：

```
登录页首屏：21 个文件，合计 3115 KB（未压缩）
  index-*.js            762 KB
  index-*.css           546 KB
  vendor-ui-*.js        364 KB
  settings-*.js         254 KB   ← 文案
  vendor-supabase-*.js  215 KB
  queue-*.js            153 KB   ← 文案
  crm-*.js              150 KB   ← 文案
  checkout-*.js         111 KB   ← 文案
  schedule-*.js         107 KB   ← 文案
  finance-*.js           79 KB   ← 文案
  rotation-*.js          76 KB   ← 文案
```

其中约 **1 MB 是多语言文案** —— 全部业务域、全部五种语言，
在用户还没登录时就全下来了。

### 为什么分块没起作用

文案按业务域分了文件，构建也确实切成了独立 chunk。但
`i18n/index.ts` 在**模块顶层**把它们全部 `import` 进来再摊平成
`translations`，而 `LanguageContext` 又静态依赖它 ——
于是这些 chunk 全部落在启动的模块图里，分块只是分了文件，没分加载时机。

### 建议（本轮未做，理由如下）

正确做法是**构建期按语言切分**：保留现有的「一个 key 五种语言写在一起」的
写法（对翻译与一致性是对的，不该破坏），加一个 Vite 插件在构建时产出
per-language 的产物，运行时只动态加载当前语言 + `en`（`t()` 的兜底链要用）。
按现在的体量，这能从首屏拿掉约 800 KB。

**没有在本轮做**：这是一次需要改构建管线和 `t()` 加载时序的架构改动，
配错的表现是整页文案空白或白屏。审查该做的是把它测准、说清楚，
不是在一轮审查的末尾把 i18n 核心重写一遍。**这个取舍请你定。**

## H-3 复核通过：没有虚拟化，但也不需要

全仓没有引入任何虚拟列表库。查下来这是**合理**的：

- 客户列表服务端封顶 200 行 —— 200 行的 DOM 在 iPad 上没有问题
- 长表格（经营数据、通话记录）同样有服务端上限
- 真正的长列表场景是打印（120 行的对账单），而那条路已有专门的
  `check-print-layout.mjs` 覆盖，且打印本来就要全量 DOM

引入虚拟化反而会和打印、Ctrl+F、读屏顺序打架。**不建议加。**
