# I 线：键盘与对比度

## I-1 ⭐ 三个手写浮层在键盘与读屏上什么都不是

绝大多数弹窗走 `components/ui/Modal`（底层 HeroUI / react-aria，
焦点陷阱、Esc、`role="dialog"` 都已经做完）。但 `Schedule.tsx` 里有三个
出于版式需要手写的 `fixed inset-0` 浮层，**一条都没有**：

| 浮层 | 用途 |
|---|---|
| `confirmModal` | 通用二次确认（含危险操作） |
| `conflictModal` | **超容量放行** |
| `cancelModal` | **取消预约** |

后两个恰恰是需要说清楚的那种操作。具体表现：

- 读屏用户**不知道弹窗打开了** —— 没有 `role="dialog"` / `aria-modal`
- 焦点仍留在背后的页面上，Tab 会走进被遮住的内容里，而那些内容是点不到的
- **按 Esc 关不掉** —— 而这个应用里其他每一个弹窗都能，这种不一致本身就是故障

**已修**：新增 `lib/dialogChrome.ts` 的 `useDialogChrome`，补齐 Esc、
焦点收进与归还、Tab 循环；`role` / `aria-modal` / `aria-labelledby` 写在容器上
（标题在哪只有调用方知道，hook 不猜）。

一处实现细节值得记下来：可见性判定**不能用 `offsetParent !== null`** ——
它依赖真实布局，在 jsdom 里恒为 null，会让「找可聚焦元素」永远返回空，
于是护栏本身失效而测试照样全绿。改用 `hidden` / `aria-hidden` / 计算样式。

## I-2 ⭐⭐ 439 处文字的对比度不合格

算的是实际色值，不是观感：

| 类 | 白底对比度 | WCAG AA | 用量 |
|---|---|---|---|
| `text-slate-300` | **1.48:1** | ✗ | 33 |
| `text-slate-400` | **2.56:1** | ✗ | **439** |
| `text-slate-500` | 4.76:1 | ✓ | 510 |
| `text-slate-600` | 7.58:1 | ✓ | — |

AA 对正文要求 4.5:1，对大字（≥18.66px 粗体 / ≥24px）要求 3:1。
而这个应用大量使用 9–11px 的小字（`text-[9px]` 26 处、`text-[10px]` 255 处、
`text-[11px]` 466 处），**没有一处够得上「大字」的豁免** ——
`text-slate-400` 在任何字号下都不合格，连 UI 组件的 3:1 都不到。

放到实际场景里：门店的 iPad 常年在射灯下、靠窗，屏幕还常带一层指纹膜。
2.56:1 在那种条件下不是「有点淡」，是**看不清**。

### 本轮没有改，这是设计决定

把 `text-slate-400` 全量换成 `text-slate-500` 是 439 处的视觉改动，
会改变整个应用的色调层次 —— 那是设计该拍的板，不是审查顺手做的事。
把数字测准、把影响说清楚，然后交给你定。

如果要改，建议按用途分两批而不是一刀切：

1. **承载信息的文字**（说明、次要标签、时间戳）→ `text-slate-500` 起步
2. **纯装饰**（分隔符、占位图标）→ 可以留，但要确认它不承载任何信息

`text-slate-300`（1.48:1）那 33 处无论哪一类都该换掉 —— 这个数字接近不可见。

## I-3 复核通过

- `components/ui/Modal` 系的弹窗（绝大多数）由 react-aria 托管，
  焦点陷阱与 Esc 行为正确
- `GuardedButton` 禁用时用可聚焦容器承载 tooltip，键盘用户能拿到禁用原因 ——
  这一点做得比多数实现都细
- 骨架屏整块 `aria-hidden`，另起可读状态文案（D 轮已验）

## 这条线没做完的部分

**没有做全流程键盘走查。** 本轮验的是弹窗这一类结构性问题，
不是「从登录到结账能不能全程不碰屏幕走完」。后者要真人按 Tab 走一遍，
或者写一套键盘路径的 E2E —— 都不是一次静态审查能替代的。
