## 2. 房间模型与 S2 的准确边界

入口：`schema/scheduling.ts`、`queries/rooms.ts`、`handlers/resource.ts`、`commands/resource.ts`、`pages/Rooms.tsx`。

已确认：

- resources 没有 active 列，容量为 integer；status 包含 available、in_use、in_service、cleaning_required、cleaning、maintenance。
- **契约 resource.save 却含 active，handler 未读取该值**。S2 必须消除静默忽略；不能把 UI 的 active=false 当成已停用证据。优先兼容映射显式 active=false 到维护流程，省略时保留状态；若采用移除字段方案，必须同步所有调用方并拒绝旧字段，而非继续吞掉。
- 类型 key 是自由文本。Rooms UI 提供 room/vip/chair/table/bed；schema 注释还含 couples_room/pedi_chair。Rooms 查询展示所有资源，不能直接用其 metrics.total 作房间数量。
- 决定按“至少一间房”严格执行：开店有效房间类型为 **room、vip、couples_room**，同 org/location、capacity>0、status 属于已知非 maintenance 状态。chair/table/bed/station/pedi_chair 不单独满足房间门禁；开放区可用 room 类型命名“大厅”。旧自定义类型不猜测改写，列修复提示；旧 active 店不降回 setup。
- resource.save 传入 resourceTypeId 时缺少显式同店类型查询。S2 同步补查类型归属，不能只依赖单列外键。
- resource.delete 的 force 会跳过未来预约检查；**不得绕过最后一间房及当前占用检查**。现有逻辑会解绑历史 appointment_items，S2 不扩大历史修改范围。

### 并发协议（S2 必须落实）

1. FinishSetup、resource.save、resource.setStatus、resource.delete 在读改前取得同一门店事务 advisory lock，建议 hash 命名空间 `setup-resources:<locationId>`；然后再取得资源行锁。
2. 在锁内查询前后有效房间数。active 门店从正数变零拒绝；既有零房间门店保留经营状态并允许修复。
3. FinishSetup 在锁内重新查询 readiness 后更新 setup→active。两种竞争顺序都测：停用先提交则开店失败；开店先提交则停用失败。
4. bus 现有锁仅保护相同幂等键；不同命令/不同 key 不互斥，不能替代上述锁。
5. 其他资源写入：`handlers/serviceResource.ts`、`staff.ts`、`ticket.ts` 和 resource 内清洁/换房流程只在服务/清洁状态间转换，不减少定义的有效房间数，不需为计数额外串行化。S2 仍保留它们原有占用锁顺序。
6. 类型删除/修改未发现独立 API handler；资源类型转换集中在 resource.save。S2 测试同店/跨店，不声明 RLS 已实测。

## 3. Readiness 接口冻结（设计）

新增 `packages/contracts/src/setupReadiness.ts` 与 `apps/api/src/queries/setupReadiness.ts`，以 contracts 根导出供消费者复用。

- 步骤 ID：store / directory / rooms / catalog / team / features / launch。
- 返回：`locationId`、`status`、`canLaunch`、`steps`（id、complete）、`missing`（code、stepId）、`warnings`（code、stepId）。返回结构化 code，前端 i18n，不返回 SQL 或英文错误文案充当翻译。
- 兼容现有 missing code：profile→store、business_hours→store、active_service→catalog、bookable_staff→team；新增 active_room→rooms。
- directory 属于引导推荐配置，目录为空给修复提示，不把旧店踢回 setup。features 显式确认用于保存进度，电话/表单均关闭仍可通过；外部号码准备状态不阻塞开店。
- S2 先完成真实可用领域，S3/S4 增补功能状态，S5 接消费者；不得在 S2 用硬编码 true 假装功能配置已完成。
- GET `/v1/desk/setup/readiness` 走 ctx + withTenant，准入沿用 settings.manage。FinishSetup 使用相同 loader，拒绝时保留既有 `setup_incomplete` / missing 字符串数组，额外附结构化修复目标，不破坏旧错误消费者。
- `SetupWizard` 与 `StepForms::launchChecks` 两处前端判断均需替换。现状后端 bookable_staff 未 join active membership，而 settings 查询已 join；共享 loader 应采用 active membership + is_bookable，补离职员工不满足开店的用例。
- 完成进度不是当前页索引；刷新初始定位到首个未完成领域；launch 完成仅在 status=active 后成立。

## 4. 健康表真实数据源与全部已发现消费路径

**纠正旧交接：实际 HealthForms 使用 `features/forms/mockData.ts::INDUSTRY_PRESETS`。** `presets.ts::FORM_PRESETS` 只有自身测试引用，且 facial key 与实际行业模板不同。S3 只抽取真实使用的行业纯数据和必需类型，不能将 mockData 中 MOCK_SUBMISSIONS 或演示 AI 摘要搬入共享包。实际六类模板 key 与 contracts/healthForms.ts 对齐；门店 businessType 当前可映射的行业由 categoryForBusinessType 决定，不能自行增加 facial 门店类型。

| 路径 | 当前行为 | 新开关接入规则 |
|---|---|---|
| `handlers/kiosk.ts::SaveFormTemplate` | max(version)+1；下架旧 active；立即发布 | 与自动首发共享 tx 内发布函数、门店/key 锁 |
| `queries/forms.ts::loadForms` | active 模板 + 历史提交/分享 | 返回真实开关及发布状态；不能只靠本地预设说已发布 |
| `kiosk/routes.ts /forms/required` | 校验 visit，选行业模板，无匹配时 fallback 任意 active 发布版 | 校验归属后判断开关；新模式要求适用行业模板，旧模式兼容单列记录 |
| iPad `CheckInLookupPage` / `WalkInPage` | 调 getRequiredForms，空则直接成功 | 使用服务端结果；无需客户端第二套开关 |
| `queries/queue.ts` | SQL 独立计算 pending_forms，行业 CASE，过期判断 | 与新开关一致；历史 signed_form_count 保留 |
| `handlers/kiosk.ts::ShareForm` | 显式 ID 或行业 active 发布模板；无模板抛错；可能通知 | 显式创建新分享在关闭时给明确未启用原因；不要自动悄悄启用 |
| web `features/forms/api.ts` / copilot `tools/healthForm.ts` | 均走 form.share | 复用同一错误与权限；二维码来自有效分享结果 |
| `public/formRoutes.ts` | token 绑定模板 ID，读取不要求当前 active | 已发链接仍按原有效期/撤销/已提交规则；关闭不撤销 |
| `SubmitForm` | 读取指定模板、签名校验、加密写入 | 不删除/改写历史，允许合法旧分享继续提交 |
| `queries/customer.ts` / forms 的历史详情 | 读提交和原模板，权限/访问审计 | 开关关闭不阻塞历史读取 |

在已搜索的 appointment handler/公开预约路径未发现以缺少健康模板阻止建预约的判断，不能报告“预约创建必然报错”。实际回归仍需 T05。Queue 与 Kiosk 对签署有效期/visit 的判断已有差异，S3 不顺手改成全新有效期政策，但必须让关闭时均不要求表单。

草稿事实：HealthForms 当前草稿在 React state，查询 refetch 新版本会覆盖对应分类；没有独立保存草稿命令。S3 自动发布不能误称这些本地编辑已发布；需要 dirty 保护，不在用户编辑时覆盖。DB 历史未发布行如存在也必须保留（数量未查）。唯一约束 `(location_id,key,version)` 已存在，仍需锁避免手工发布/首发不同 key 重试产生竞争失败。

## 5. 电话接口与旧配置兼容

- `RequestAiVoice` 仅 upsert main/transfer_target，校验转接成环，返回 active ai_voice 号码；不持久化申请意愿，不是新功能开关。
- `SettingsSavePhoneAssistant` 写 settings.phone_assistant（兼容 phoneAssistant），autoBookEnabled 是订预约偏好，不是 ai_answer。
- `SavePhoneLine` 已有新线默认 false / 省略保留 ai_answer；数据库默认见 0113。`telnyx/routes.ts` 配置响应查不到 active ai_voice 时返回 aiAnswer=false。
- `bindAiLine.ts` 用门店 owner/manager context dispatch SavePhoneLine，省略 aiAnswer；不能在 DTO 中把号码存在等同“已开启”。
- **额外缺口：SavePhoneLine 只有 settings.manage，没有 system:true；通用 HTTP 命令入口可达。** 现状并不满足“仅平台可分配号码”的强保证。S4 必须拆开平台绑定与店主启用/话术命令，保留 CLI 经可信 server-origin 调用；检查全部调用方，新增店主伪造绑定被拒测试。只隐藏向导输入框不足以满足要求。
- `assistant_id` 缺失时具体供应商接听是否可用，当前静态代码不能证明；本地 configured 与真实 provider-ready 必须区分。五态中的失败/暂停仅凭持久化证据显示，不能伪造供应商健康检查结果。
- `ai_voice_requested` 记录意愿；绑定不自动开启，即使之前已申请也仍须对就绪线路显式开启。关意愿时关闭当前线路；开启动作在同一事务校验配置并设置 ai_answer。历史开启线路没有新字段时保留原行为。
