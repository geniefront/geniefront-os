## 2. 术语与范围

- **单项目 service**：一个可履约的项目。
- **加项 add-on**：附着于具体服务的额外内容，可能收费或增加时长。
- **组合套餐 service bundle**：一次消费中的固定组成项目，采用固定组合价。
- **次卡 prepaid package**：购买后留在顾客账户，跨消费按次数/权益核销。保留既有含义。
- **套餐实例 bundle instance**：某次预约/工单实际选购的一份套餐。买两份产生两个实例，不能仅靠模板 ID 分组。

首版完整范围：固定组成、支持重复项目数量、子项目级 add-on、多技师执行、预约和 walk-in、套餐分组、结账与退款、提成与报表、导入与手动管理、已有顾客侧入口。

不纳入首版：任选 N 项、套餐嵌套、跨多次到店履约、跨顾客共享同一套餐、自动续费、在线支付或 POS 集成、复杂并行模板编辑器。现有并行服务不能被破坏，但不自动把套餐子项目安排为并行。

## 4. 默认业务规则

### 4.1 组成、数量与版本

- 套餐选择至少两个实际组成单元，可为不同项目或同项目两次；数量正整数并设置合理上限。
- 重复项目按执行单元生成独立 item，具备独立实例子项 ID，不能对 service_id 去重。
- 模板可保存名称、描述、组成、数量、排序、总价、线上可预约状态、包含和允许额外购买的加项。
- 首版组合价不超过组成原价合计；零价允许与否复用门店现有免费服务权限，不能静默免费。
- 模板变更有版本；下单锁定当时价格、名称、组成、时长和关键财务属性。模板停用或改价不影响历史订单。
- 已停用子项目不能用于新建套餐订单；编辑模板明确显示需要修复。历史执行不得因目录停用突然打不开。
- 用户明确选择套餐才享受套餐价；散选相同项目不自动改价。

### 4.2 加项

- 从套餐入口点加项后选择具体子项目；不创建无归属的“整个套餐加项”。
- 模板内包含的 add-on 计入套餐组成及原价基础，但不额外再收费；额外 add-on 按正常价格追加，不自动享受套餐折扣。
- 每笔 add-on 保存 serviceId、名称、目录价格、数量、时长、是否套餐包含、所属执行子项和税务属性快照。
- 普通附属加项跟随主项目执行；需要独立技师/资源/开始完成的内容，应作为独立执行子项目建模。
- 若用独立财务明细表示加项，不让它自动生成第二个执行任务或重复轮牌；若继续合并主项金额，也必须保留可核对的定价明细。
- 付款后加项必须通过现有支付阶段/追加结算能力核查；若现有模型只允许一次服务结算，需实现关联追加单/补差账务流程，不能直接重开已结算阶段或覆盖原收款。

### 4.3 履约与排程

- 默认按模板顺序排时间；起止时间由子项目、加项、缓冲与 active/wait 规则计算，不能只把名称连成一个大项目。
- 每个子项目分别校验技师技能、人数要求、时段和资源；首版按顺序，无需新增复杂并行 UI。
- 套餐父分组不占资源、不增加顾客人数、不独立计轮。子项目沿用现有轮牌规则，额外回归同一顾客多项目不会意外多占容量/重复计轮。
- 只有全部有效执行子项结束，套餐履约才完成；取消项单独显示，不能伪装为完成。
- 履约状态和付款状态独立。先付款不意味着服务已完成；最后一个项目完成不能重复收款。
- 整套改期/移除事务化，任意子项冲突则整体失败并给可理解的原因；不得留下半套记录。

### 4.4 删除、替换与调整

| 时机 | 默认允许行为 | 金额规则 |
|---|---|---|
| 未开工、未付款 | 整套移除；明确拆为单项；更换整套 | 拆单前展示新价，确认后按该订单锁定的单项原价重算，保留来源 |
| 部分开工、未付款 | 已做项目保留；授权调整未做部分，需原因 | 不静默取消套餐价；明确展示原净额、调整额、新应付 |
| 已付款 | 加项补差、部分或全额退款 | 追加业务记录，不覆盖原快照、原付款或原提成 |
| 已日结封账 | 沿用既有重开/跨日退款政策 | 不绕过日结锁定，不改历史营业日报 |

首版不提供任意替换套餐内部项目的快捷按钮；需要替换时走明确拆单或调整流程。部分开工后的默认取消金额按锁定的子项净额释放，剩余已做项目保留其分摊价；若门店要求取消后失去套餐优惠，作为后续显式政策，不能自动追收。

### 4.5 优惠、次卡与提成

- 套餐内建优惠与额外整单优惠分开记录；默认套餐部分不自动叠加优惠券。混合单中符合条件的散项仍按既有优惠券规则处理。
- 权限允许的手动优惠可以应用，记录原因，服务端检查范围和上限。
- 次卡不默认覆盖套餐子项；同单散项仍可按既有规则核销。不能按 service_id 匹配时误把套餐子项再次全额覆盖。
- 财务营收按分摊实售额；提成遵守现有显式“原价/折后”等门店薪酬政策，不能把营收基数直接替代提成政策。
- 不复用 packageCommissionBasis 作为新组合套餐开关，除非已明确完成政策兼容设计与测试。
- 小费保持既有金额/工时/角色分配规则；不默认把套餐优惠分摊比例作为小费比例。

## 5. 数据模型建议与不变量

### 5.1 新增目录实体（建议名称）

- service_bundles：租户/门店、名称描述、固定总价、active、online_bookable、version、sort、时间戳。
- service_bundle_components：bundle_id、稳定 component_id、service_id、qty、seq、包含加项配置；同租户同店引用。
- 加项适用性关系：复用已有可适用服务关系；若不存在，增加明确关系。不要用名称匹配运行时加项。

目录中既有 services 保持实际服务语义。推荐套餐用独立选择项，不创建一个可以误履约、误计税或误计轮的虚拟 services 父项。

### 5.2 订单实体

建议一份稳定的 order_bundle_instances 关联 appointment_id（可空）与 ticket_id（可空），预约转工单时保留同一实例身份；至少一个归属存在，且归属必须同租户、同门店、同顾客。也可采用预约/工单各自实例，但必须有显式不可歧义的来源映射。

实例快照包括：template_id/version、名称、原价合计、套餐净额、优惠额、币种（按系统已有约束）、创建来源、取消/拆单状态。历史财务字段不可随模板更新重写。

appointment_items 和 ticket_items 增加可空 bundle_instance_id、bundle_component_instance_id 以及明确的预约子项来源关系。普通历史行均为空。不要按数组 seq 配对作为唯一关联，更不能用 service_id 配对。

原价、套餐分摊价和加项明细可使用规范化表或严格类型化快照；可查询的归属、数量、金额与租户约束不应只藏在任意 details JSON 中。

### 5.3 强制不变量

- 每个套餐实例的包含明细净额之和 = 实例锁定套餐价。
- 每笔优惠分摊之和 = 该笔优惠；任何明细净额非负；退款累计不超过可退余额。
- 模板 ID 不是订单分组 ID；component ID 不是重复执行单元 ID。
- 父套餐无额外收款行；子项目与加项不重复计价。
- 每个预约子项最多映射一次有效工单子项，开单/重试不会重复展开。
- 并发改价、付款、加项和退款有事务锁/版本校验，旧报价不能覆盖新订单。
- 报价只由服务器根据有权限读取的目录/快照计算，不信任客户端传入优惠金额和分摊值。
- 模板更新和订单执行均满足 RLS；跨店套餐或跨店子项请求必须失败。

## 6. 统一计价与账务适配

先调查 total_cents、discount_cents、subtotal_cents 在税、提成、退款、报表中的实际含义，产出字段口径表，再决定映射。现有 recalcTotals 求和 total_cents；如果 total_cents 已是套餐净价，又把同一优惠放进下游会扣的 discount_cents，会二次打折。

推荐共享函数职责：解析套餐 → 展开组成 → 锁定报价 → 分摊组合价 → 加入额外加项 → 分摊额外优惠 → 返回执行项目和财务明细。命令处理层负责查询、鉴权、锁与事务，纯计价函数不访问数据库。创建入口、预览和结账复核共用它。

### 6.1 示例（均为税前，无额外优惠）

| 明细 | 原价 cents | 分摊净价 cents |
|---|---:|---:|
| A | 10000 | 8824 |
| B | 5000 | 4412 |
| C | 2000 | 1764 |
| 套餐 | 17000 | 15000 |
| B 额外加项 | 1500 | 1500 |
| 服务合计 | 18500 | 16500 |

使用确定性的最大余数法按原价权重分摊；余数相同按稳定组成顺序/ID 决定，不能受数据库返回顺序影响。先规范执行单元再分摊，重复项目不丢失。全部权重为零时只允许零套餐价，否则报校验错误。

- 收据可显示原价 170、套餐优惠 20、套餐价 150、加项 15；机器账务不能重复扣 20。
- 商品/服务混合税属性按明细快照接入现有税引擎，父行不重复计税；税规则由门店配置决定，本计划不新增税务法律结论。
- 额外整单折扣只分摊到符合条件的剩余金额，再计算既有税费/附加费规则；禁止以套餐目录原价再次作为剩余应付。
- 退款根据最终已支付明细净额、已分摊额外优惠与税/费快照计算，并扣除历史已退；有额外优惠时不能直接退上表示例的 1764。
- 没有额外优惠/税/费时退 C 为 1764；套餐剩余服务金额为 13236，加项不受影响。
- 提成冲销必须遵守原提成政策和分配结果，不按当前模板、当前费率重新计算历史工资。
- 合并付款仍按每位顾客一张 ticket，套餐实例不能跨 ticket 分摊；付款方式、找零、小费按既有组单算法处理。

| 看板卡片 | 套餐名称、套餐价、子项数、完成进度；展开子项与加项；避免三个顾客卡片代表一位顾客 |
| 看板操作弹窗 | 派单、开工、完工、换人、加钟/项、回退、作废均理解套餐关系 |
| 技师端 | 只呈现权限范围内的实际任务，带套餐上下文与加项；不会看到无关子项顾客隐私；权限允许才显示金额 |
| 健康表/服务单 | 按所有实际子项目汇总需求，不按不存在的父服务 ID 查；沿用原有去重和访问权限 |
| 独立 Checkout / 看板 Checkout | 两入口金额一致；组合优惠与额外折扣分开；付款阶段、散项次卡、合并支付兼容 |
| 历史工单/收据/打印 | 保存当时套餐名和组成，退款后展示调整；不因目录改名而变历史 |
| 营业数据/员工收入/日结/CSV | 套餐销量与子项执行量分别汇总；营收仅计一次；毛额/优惠/净额口径明确 |
| 在线预约 apps/booking | 目录选择、时隙、报价、创建、查看、改期/取消完整覆盖；服务端验证组成版本 |
| iPad/kiosk | 套餐选择与签到保留归属；入口能力不足时给明确人工办理提示，最终补齐适用创建流程 |
| AI 副驾/电话 | 目录明确区分组合和次卡；工具参数传套餐 ID；不得 AI 自算折扣/时隙；电话原有权限限制保持 |
| 通知与实时刷新 | 预约消息按套餐及必要子项展示；事件使看板、日程、技师、结账同时失效刷新；无重复通知 |
| 旧客户端/断网 | 旧客户端不能将套餐价当单项价乱改；断网只读仍能看到缓存中的分组和正确金额 |

## 8. 实施任务与依赖

### P0：代码复核与口径冻结（约 0.5–1 天）

- [ ] 读取约束、记录基线，枚举所有创建/修改/结算入口及测试位置。
- [ ] 明确旧字段含义与各消费者，特别是折扣、提成、退款和支付阶段。
- [ ] 确定实例生命周期、加项明细存法、字段映射和追加结算方案。
- [ ] 记录建议规则与已有真实门店政策冲突；无冲突按本计划继续。

交付：入口矩阵、字段口径表、最终模型决策。后续不能各端自行决定金额口径。

### P1：模型、迁移、契约、纯计价（约 2–3 天；依赖 P0）

- [ ] 新表、快照、约束、RLS、索引、迁移注册与空库/升级兼容。
- [ ] 定义套餐管理与报价/展开契约、错误码，更新命令注册和权限。
- [ ] 实现共享展开与整数分摊；数量、重复项目、加项、零金额、尾差测试。
- [ ] DTO 支持 nullable 套餐字段，普通订单保持兼容。

交付门槛：纯函数测试通过，租户隔离通过，旧单金额不变。

### P2：导入与套餐目录管理（约 1.5–2.5 天；依赖 P1）

- [ ] AI schema（包括 compact 版本）、提示词、归一化、翻译、草稿契约同步扩展 bundle。
- [ ] 导入审核字段与匹配 UI，显示未解析组成；名称歧义必须选择 ID。
- [ ] 发布按类型分流；普通服务先解析，再建套餐，事务回滚与重试幂等。
- [ ] 项目管理和向导支持套餐 CRUD、数量、包含加项、价格与状态。

交付门槛：同一导入样本含普通项、加项、组合、10 次卡，四者落库正确。

### P3：创建、预约与工单展开（约 2–3 天；依赖 P1）

- [ ] 内部预约、walk-in、直接 ticket.open 共用解析与报价；不依赖前端自行展开。
- [ ] 预约转工单使用稳定来源映射，并原样继承实例及快照。
- [ ] 整套创建/改期/移除、拆单、版本冲突、并发重试。
- [ ] 子项目资源、技师、时长、加项校验；相同项目与多份套餐不混淆。

交付门槛：两份同模板套餐加散项，开单后分组与总价准确且无重复。

### P4：看板与履约（约 1.5–2.5 天；依赖 P3）

- [ ] 查询 DTO、卡片分组和进度、动作弹窗、项目级派单/开始/结束。
- [ ] 加项/加钟归属、部分完成与回退、取消展示、拆单及调整预览。
- [ ] 技师端、服务单、健康表、实时通知和缓存失效。
- [ ] 前台单端全部可操作，父套餐不重复占资源和计轮。

交付门槛：三子项由两名技师执行，完成 1/3 时整单不会提前完工。

### P5：结账、退款、提成与报表（约 2–3 天；依赖 P1、P3）

- [ ] 统一结账预览/提交；额外折扣、税、附加费、次卡排除范围。
- [ ] 两个 Checkout UI、先付后做、分阶段小费、现金/刷卡混合、组单。
- [ ] 付款后加项补差、退款余额和冲销、日结限制，幂等与竞争测试。
- [ ] 原价/折后提成、双技师分配、退款冲销；小费规则不漂移。
- [ ] 收据、历史工单、员工收入、营业日报/CSV 明确口径。

交付门槛：所有钱与支付记录/退款/收入对平，不存在父子重复计费或二次优惠。

### P6：顾客端与 AI 入口（约 1–2 天；依赖 P3、P5）

- [ ] booking 套餐目录、时隙、创建与后续管理。
- [ ] kiosk 适用流程、签到保留分组和报价。
- [ ] 副驾与电话目录、工具契约、错误反馈、现有权限策略。
- [ ] 通知与多语言；未支持阶段进行显式入口保护，完成后移除过渡限制。

交付门槛：不同入口同一选择生成相同组成与金额。

### P7：历史数据与上线准备（约 0.5–1 天；依赖 P2–P6）

- [ ] 提供只读历史 package 候选扫描，列出可能的组合；不能只凭 sessions=0 或 1 自动判断。
- [ ] 提供逐条确认转换流程/脚本设计，保留原 ID 映射；已售次卡权益与历史单不自动迁移。
- [ ] 加法式迁移顺序、旧版本兼容、功能开关、新创建停用方案。
- [ ] 回退只关闭新销售，保留已有套餐的查看/履约/结算能力；不可删除已使用的新表。

交付门槛：升级后旧单/次卡可用；回退策略不会让新套餐成为孤儿订单。

### P8：完整验证与交接（约 1–2 天；依赖全部阶段）

- [ ] 完成下节测试矩阵、受影响包的 typecheck/build、守卫与隔离库测试。
- [ ] 浏览器验证完整前台闭环，补测 booking、ipad（现有 E2E 不自动启动它们）。
- [ ] 多语言、时区、触屏和断网场景记录。
- [ ] 实施报告填写已完成、未完成、测试命令与结果、证据、风险、生产操作清单。

时间为单名熟悉仓库工程师的粗估，总计约 12–20 个工程工作日；不是承诺，也不能用估时作为省略链路的依据。

## 10. 完成定义与交付格式

必须同时满足：

- [ ] P0–P8 有实际实现和证据；不支持项明确列出，不能暗中降级用户范围。
- [ ] 从导入/手动新建套餐开始，真实 UI 能跑完选套餐、加项、看板、派单、服务、付款、收据。
- [ ] 部分退款、付款后加项、次卡混合、提成和日结都有测试支持。
- [ ] 同一金额口径在前台、顾客端、AI、数据库与报表一致。
- [ ] 迁移、RLS、权限、幂等、并发、旧数据和回退策略完成。
- [ ] 没有未授权生产变更，没有依赖短信、iPad、技师手机才能闭环的步骤。

执行者最终报告建议另存 `docs/plans/2026-09-07-service-bundles-implementation-report.md`，包含：

1. 实际采用的模型与相对本计划的变更理由。
2. 入口矩阵和字段口径表。
3. 每阶段完成状态、主要文件和迁移顺序。
4. B01–B32 对应测试名称/证据路径、通过/失败/未执行及原因。
5. 实际运行命令与结果，未验证环境和剩余缺口。
6. 历史 package 处理方案与待执行的生产操作，不含凭据或客户隐私。
7. 可供用户复现的最短完整操作步骤。

不要提前创建虚假的通过报告。文档或代码写完、typecheck 通过，均不等于业务验收完成。
