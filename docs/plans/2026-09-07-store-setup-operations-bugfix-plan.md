## 2. 目标开店流程（U01/U02/U04/U08）

建议使用 7 个清楚的领域步骤，iPad 上用“第 N/7 步 + 当前名称 + 可打开的步骤列表”，不把七个长标题挤成一行：

1. **门店资料**：店名、行业、联系方式、门店时区、营业时间。
2. **员工基础设置**：岗位、职级、技能；按行业一键生成少量常用项，预览后可编辑。
3. **房间设置**：创建至少一间启用的房间，填写名称与正整数容量；开放区可命名“大厅”，复用现有房间/资源模型。
4. **服务项目**：拍照导入或手动创建；价格、时长、分类、所需技能、同时技师人数、网约开关。
5. **员工与排班**：从已有目录选择岗位、职级、技能，至少一位可接单员工；服务实际可由足够人数履约。
6. **功能设置**：AI 电话默认不启用；健康表默认不启用。开启健康表时自动初始化并发布行业默认模板；AI 未分配线路显示“AI 电话设置中，等待平台分配号码”。
7. **检查并开店**：展示真实后端检查结果和修复跳转。未分配电话不阻塞开店；健康表关闭不阻塞预约或签到。

业务基线：

- 字典设置必须在项目与员工之前出现；新店每类至少保留一个可用选项作为建议基线。执行时不要把已有营业中的空目录门店踢回向导。
- “房间至少一间”是本次用户明确要求，不是可以略过的可选项。检查的是当前门店可用的房间，不是任何 resource 行。
- 不把每个员工都要求拥有所有技能，也不自动把每个项目绑定全部技能。
- 不强制启用 AI/健康表/短信才能开店；开关关闭时核心前台能独立闭环。
- 进度从持久化数据推导，刷新、重新登录和换设备一致；不要只靠当前 step index/localStorage 假装已保存。

## 3. W0：短信归属与数据隔离（U09，先处理）

### 3.1 已发现的链路

- `apps/api/src/telnyx/routes.ts` 的 `handleInboundSms` 保存 from/to/body/intent/providerId；当前没有门店归属解析。
- `packages/db/src/sms.ts` 保存平台级 `sms_inbound`。
- `apps/api/src/queries/smsInbound.ts` 先找在本店有预约的客户电话，再按 `from_e164` 取消息，不核对 `to_e164`。
- `packages/db/sql/0079_sms_inbound_isolation.sql` 的 SELECT policy 只判断 `customers.org_id = app_org_id()` 与来信手机号，连 location 也没有细分。
- 所以代码能够证明“同号客户跨店共享正文”的路径存在；不能直接宣称生产上任意店无条件看到任意短信，生产迁移和查询路径仍要核实。

### 3.2 归属规则

1. **发往店铺独立号码**：按短信接收时有效的号码归属，唯一映射 org/location。店铺能查看该号码收到的相关消息，包括还未成为客户的新客咨询。
2. **平台共享号码的 START/STOP/HELP 等系统关键词**：平台留存、处理订阅状态；默认不在任何店的正文列表显示。不要为了隐藏消息删除平台的订阅/退订处理。
3. **平台发出的预约通知**：已有 outbox 的 org/location/entity 关联可以安全用于“本店发出消息/送达状态”的展示。
4. **客户回复平台号码**：只有存在可靠且唯一的会话/预约归属证据时才显示给一个目标店；不能靠“最近发过短信”“存在未来预约”“同号客户”猜测归属。
5. **无法确定的共享号码回复**：按用户给出的降级许可，不显示在店铺端。普通短信未必有 reply-to 消息 ID；不要承诺仅靠一条 START 能可靠关联到某家店。

### 3.3 实施步骤

- [ ] 枚举入站列表、会话详情、未读数、沟通日志、通知、搜索/导出、实时订阅、平台测试收件箱的全部读取路径。
- [ ] 设计 `routingScope`（store/platform/unresolved）与 nullable org/location、归属证据、接收时号码绑定记录。可直接扩展入站表，也可独立可见性映射；所有消费者共用规则。
- [ ] webhook 验签后先规范 E.164，再解析 To；记录时固定归属。未知/多义号码进入 platform/unresolved，不广播给所有匹配客户。
- [ ] 处理号码转让/重新分配：历史短信按接收时归属保存，不能查询时连接“当前号码归属”使新店读到旧店内容。
- [ ] provider 消息 ID 唯一去重；重放不增加未读或重复通知。事务保证入站与归属不产生可见的半成品。
- [ ] API 和 RLS 都要求明确的 org + location 归属；跨店直接查消息 ID 也拒绝。
- [ ] 店铺客户关联仅用于该归属下的姓名展示，不能反向决定授权。避免同 org 不同门店的关联预约详情泄露。
- [ ] 旧记录只在有可靠证据时回填；无归属记录保持平台可见，不按客户手机号批量归店。保留原始记录供授权平台排障。
- [ ] 界面计数/日志同步收窄；显示“平台系统回复由平台处理”说明即可，不展示无关正文。

最小修复也必须覆盖读取、RLS 和派生通知；只从 Messages 页面过滤 START 不算完成。

### 3.4 验收

- 同一手机号在 A/B 两店建客户与预约，给 A 独立号发消息，仅 A 能读。
- 同 org 的 A1/A2 两店也隔离；客户没有预约仍能给店铺号发咨询并被正确店看到。
- 向平台号发送 START，平台订阅处理正常，所有门店正文列表/计数/日志都不出现这条消息。
- 给平台号回复但无法唯一归属时，各店均不可见；有可靠绑定时仅目标店可见。
- A 店猜测 B 消息 ID、查询数据库受限角色、监听实时更新均不能获取 B 正文。
- webhook 重试、未知号码、线路换绑、历史数据回填均不串店；平台运营的合法排障仍可用。

## 4. W1：默认设置、健康表首发、房间门禁和 AI 线路（U01/U08）

### 4.1 入口与根因

向导：`apps/web/src/pages/SetupWizard.tsx`、`features/setup/flow.ts`、`StepForms.tsx`。  
后端：`apps/api/src/handlers/setup.ts` 的 FinishSetup；契约 `packages/contracts/src/commands/setup.ts`；设置 DTO/API 在 `features/settings/` 和 `apps/api/src/queries/settings.ts`。

健康表：`HealthForms.tsx` 首屏从行业预设生成本地草稿，显示有内容不代表已落库。`handlers/kiosk.ts` 的 SaveFormTemplate 才写 `published_at`；ShareForm 默认要求 active + published + 匹配行业 key，没有则报 `no_active_form_templates`。这是“需要手动先发布一次”的明确解释；用户所说“无法创建”具体指分享/预约/其他入口，实施时分别复现，不笼统判定预约写入一定失败。

电话：`packages/db/src/schema/phone.ts` 默认 ai_answer=true；`handlers/phone.ts` upsert 在未提供 aiAnswer 时写 true 并更新旧值；`telnyx/routes.ts` 获取电话上下文也有 true fallback。`locations.settings.ai_change` 是 AI 改期/取消策略，不可用它代表电话开通状态。

### 4.2 设置模型与生效规则

建议保存明确的门店功能配置，至少区分“未初始化/已显式选择”和 enabled=false，不把字段缺失任意解读成 true。已有等价字段应复用并提供唯一读取函数。

健康表：enabled=false 为新店默认；enabled=true 的成功响应必须意味着存在适用的已发布模板。关闭后停止自动要求新表，不删除历史签名，已发链接是否继续有效须沿用现有有效期/撤销规则并在实现报告写明。

AI 电话应分为两个维度：门店启用意愿与平台线路准备状态。建议展示状态：

| 状态 | 展示 | 接听行为 |
|---|---|---|
| 未启用、未分配 | 未启用；AI 电话设置中，等待平台分配号码 | 不接听 |
| 已申请启用、未分配/配置中 | AI 电话设置中 | 不接听 |
| 已分配且准备完成、仍关闭 | 号码已就绪，尚未开启 | 不接听 |
| 已准备完成且显式启用 | 已开启 | 经原有权限、余额与接听策略检查后接听 |
| 配置失败/线路暂停 | 配置失败或暂停，提供已有支持入口 | 不声称正常接听 |

用户会在后台分配号码：号码分配只由现有平台/运营授权入口执行，不新增店家随意输入任意号码即可绑定的能力。分配号码本身不得默认开启接听；显式开启由已有授权开关或运营显式动作完成。

### 4.4 旧店兼容与验收

迁移先只读统计：新店缺配置、已有发布模板、现有开启线路、房间为零的营业中门店。新默认只用于新店；历史缺值根据明确使用证据制定回填报告，不全量强制关闭。已营业但无房间的店显示修复提示，不直接改 status 使其无法经营。

验收：全新门店两个功能默认关闭；零房间不能开店；一间有效房间可通过；启用健康表一次即可生成有效表单且重试不重复版本；关闭时普通预约签到不受阻；平台未分配电话时可以开店，分配后仍关闭，显式启用后才可接听；其他 AI 权限保持原策略。

## 6. W3：预约日期、时长、详情状态与下一步（U03/U06/U11 前半）

### 6.1 日期问题：先区分三种日期

`apps/web/src/context/ScheduleContext.tsx` 从 useBusinessDay 初始化 currentDate。`components/CreateAppointmentModal.tsx` 使用 defaultDate || currentDate，而默认时间使用浏览器 getHours/getMinutes；提交用 wallMinutesToInstant(date,time,timezone)。这使“营业日日期 + 浏览器当前钟点 + 门店时区”可能混用。

举例：纽约门店 9 月 7 日 01:00，cutoff=04:00，营业日是 9 月 6 日，但新建“现在”的预约日历日期应为 9 月 7 日。不能简单把 useBusinessDay 改成日历今天，否则队列和报表会错。

建议明确入口语义：

| 入口 | 日期/时间来源 |
|---|---|
| 点击日历具体格子 | 格子对应的真实门店日历日期与钟点（跨午夜需 day offset） |
| 日历页顶部新建 | 当前选中日期；页面明确显示，用户正在看昨天时不偷偷改今天 |
| Dashboard/全局“新建预约” | 门店当前日历日期与门店当前时间，按既有步长取整 |
| 历史补录 | 用户明确选择的过去日期，保留现有补录确认/权限 |
| 未来日期 | 使用当天可用营业时间，不把浏览器今天的钟点无条件套进去 |

### 9.2 生日日期选择

入口：`apps/web/src/pages/PublicHealthForm.tsx` 的客户生日与通用日期题、`apps/ipad/src/pages/HealthFormPage.tsx`；再搜索健康表其他渲染器与客户档案 DOB 输入。

- [ ] 生日用可直接输入的年/月/日字段或支持年份直达的选择器，推荐三个明确字段，年支持 4 位数字输入，月/日可选择；不需要逐月点击几十年。
- [ ] 共用日期验证规则，采用 date-only `YYYY-MM-DD` 存储，不转换 UTC timestamp。不要用营业日 cutoff 判断一个人的生日。
- [ ] 支持 1940/1960/2000 年直接输入，闰年 2/29，切换月后的非法日提示；不能把 2 月 31 日静默变成 3 月。
- [ ] 不接受未来生日；比较基于明确的门店日历今天，未加载时不先用设备/UTC 日期提交错误判断。不要无依据增加成年人/最小年龄限制。

- [ ] iPad Safari、外接键盘、数字键盘与 VoiceOver 可用；字段关联 label 与错误提示，按钮触摸面积约 44px 及以上。

验收：用户可直接输入 1965-03-12 而无需按月翻页；2000-02-29 成功，1900-02-29 拒绝；留空与未来值处理正确；跨时区保存再打开日期不变。

### 9.3 iPad 范围和布局规则

“适配 iPad”首先是 **apps/web 前台在 iPad 上操作**，同时覆盖 apps/ipad 顾客自助、apps/booking 及公开健康表。按照用户“所有 UI”要求，apps/platform 和 apps/marketing 也需做页面级平板扫屏；apps/ios 是空壳，不属于可适配页面。

建议视口以 CSS 像素为准：768×1024、820×1180、1024×768、1180×820、1024×1366；另测约 600px 分屏宽度和 390px 手机回归，实际 Safari 地址栏/键盘会缩小可用高度。

布局规则：

- 全局内容区域不出现无意义横向溢出；排班时间轴/宽表可在明确标示的局部容器横滚，不把页面整体推出屏幕。
- 侧栏宽度按可用空间折叠，不能占掉竖屏大半工作区；抽屉支持触摸关闭、点击遮罩、键盘 Escape。
- flex/grid 容器检查 min-w-0/min-h-0 与 shrink；主要列竖屏堆叠，工具条换行，长姓名/分类/译文不遮挡按钮。
- Modal/Drawer 用动态可视高度与内部滚动；表单内容可滚到底，保存/取消在软键盘弹出时仍可达，不用 body overflow-hidden 把唯一滚动通道堵住。
- 固定底栏考虑 safe-area；焦点不被遮罩或 sticky footer 覆盖；嵌套滚动避免手指滚错区。
- 所有依赖 hover 的菜单提供点击入口；拖拽排班/排序要有点击编辑/上移下移替代，不能要求鼠标才能完成核心流程。
- iPad 上输入字号尽量不低于 16px，避免聚焦缩放；交互目标至少约 44px；不要为塞下信息继续缩小字体。
- 加载、空态、错误、无权限以及真实大量数据都测试，不只截图空白列表。
