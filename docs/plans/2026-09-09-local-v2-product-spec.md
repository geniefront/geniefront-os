# GenieFront 本地新版产品规格 v1

日期：2026-09-09。基线：`807b773`。依据：[需求扫描底稿](2026-09-09-product-requirements-discovery.md)。

用户已授权由执行方决定需求整理与交互设计，并明确所有行业重要、本地体验满意后才替换现有版本。本文固定本地新版的目标行为与验收口径；尚未实现的内容不得据本文标成完成。没有创建 Goal 或启动整库重写。

## 1. 产品决定

1. **行业全部保留。** 覆盖 nail、massage、foot_spa、lash、scalp、hair 和 mixed。行业提供预设与术语；规则由实际服务、员工、资源和店规决定，不按行业名硬分叉。
2. **前台独立营业。** 不依赖技师手机、iPad、AI 电话或短信就能跑完整天。
3. **一客一张营业卡，项目逐项执行。** 卡片汇总客人的进度，每个项目保留各自技师、资源、时间和状态。多人付款时关联单据，不把多客揉成一个不可拆的项目集合。
4. **履约与收款分开。** “已经付款”不代表“服务完成”，“完成一项”不代表“整单可以归档”。资源释放跟随实际履约，不能等收款才释放。
5. **设置少打扰营业。** 前台默认进入今日营业；老板保留完整设置。现有功能可重新归组，不能因收起菜单而丢失入口。
6. **本地可比较。** 新版独立目录、端口、数据库与模拟收件箱；旧版及原始数据保留。切换生产与历史数据迁移另行验收。
7. **保留可靠资产。** 继承命令契约思想、金额引擎、权限、租户隔离、幂等、审计和历史故障场景；按需要改造实现，不以全部文件重新敲一遍作为目标。
8. **真实结果优先。** 保存失败不显示成功；模拟外部服务必须标明；健康表规则提示与模型摘要分别标识来源。
9. **建站继续人工代办。** 用户提交需求和资料，由平台经营者制作并交付，保留现有申请、进度、修改意见、预览和上线申请流程。当前不建设用户自助建站器，不引入 Puck、Payload 或自动建站/发布平台。
10. **保留现有 UI、Kanban 与自定义日程的优点。** 用户认可当前风格，重构重点是缺陷、一致性与内部结构。此前新视觉样板和通用日历替换建议不作为实施基线。架构、技术栈与阶段计划以[新版重构计划](2026-09-09-v2-refactor-architecture-plan.md)为准。

## 2. 角色与界面结构

| 使用者 | 默认工作区 | 必须完成的事 |
| --- | --- | --- |
| 前台/店长 | 今日营业 | 预约、签到、派单、逐项服务、调整、收银、交接；权限允许时日结 |
| 老板兼技师 | 今日营业，可切技师工作区 | 管店与接客可兼任，权限和可接单资格分开 |
| 技师 | 今日任务 | 开始/完成、服务注意事项、打卡、收入明细；客户联系方式按权限脱敏 |
| 顾客 | 手机预约或到店 iPad | 预约、自助管理、签到、表单；不能接触门店后台 |
| 平台运营 | 独立运营后台 | 开店、订阅码、线路配置、支持/建站工单与运营审计 |

门店后台可按以下六个业务分组组织代码与功能清单。实际导航以现有 UI 为基线，只有验证改善操作路径后才调整，不强制重排用户熟悉的入口：

| 分组 | 二级工作区 |
| --- | --- |
| 今日营业 | 营业卡、日程、房间工位、即时轮牌 |
| 预约与客户 | 预约列表、客户、健康表、客户沟通历史 |
| 订单与收银 | 工单、待收款、退款/作废、付款凭证 |
| 员工与收入 | 员工、岗位职级技能、班表、考勤、提成、小费发放、轮牌规则 |
| 经营与增长 | 日结、报表、礼品卡/次卡/优惠券/积分、评价、消息、建站服务 |
| 门店设置 | 服务及组合套餐、资源、营业时间、角色权限、功能/AI/设备、订阅额度 |

移动端使用同一权限与业务规则；触屏入口完整可点，拖拽仅作为辅助。视觉采用中性底色、深色正文、克制的青绿色主动作；状态同时用文字表达。错误提示说明影响与下一步。

## 4. 状态与动作的统一规则

后端返回明确事实与当前允许动作；前端展示、收集输入，不另造第二套金额或冲突判断。离线快照只读。

| 对象 | 状态/事实 | 关键约束 |
| --- | --- | --- |
| 预约 | 已约、取消、未到等计划状态 | 预约存在不等于实际在场，也不等于已开工 |
| 到店记录 | 到店、候客、入座、离开 | 取消预约需要处理相关候客记录；不产生幽灵卡片 |
| 服务项目 | 待开始、进行中、已完成，以及撤销事实 | 项目可以有独立技师与工位；开始失败不能制造占用 |
| 付款 | 服务款、小费、合并款、退款及结清事实 | 付款与履约独立；每次收款有独立幂等键 |
| 资源位置 | 可用、实际服务、待清洁、清洁、停用 | 实际服务释放与清洁分阶段；多人位置互不误清 |
| 营业卡 | 由以上事实推导 | 不允许靠拖进某列伪造服务或收款状态 |

主动作按以下顺序确定：未到店先签到；缺派单先安排；按店规需预收则先收款；需要开始/完成则推进项目；全部完成后收剩余款；服务与钱都结束才归档。并行项目保留逐项操作，不能强制将本来可并行的服务串行。

“回退”只撤销指定业务效果，先展示会重开的项目、资源影响以及是否涉及钱。付款退款使用独立动作，不能靠回退状态暗中退款。已发收入的后续退款产生可追踪调整，沿用当前账务规则；不得悄悄改写既有发放事实。

## 5. 样板流程 F01：一客两项、中途加项、两位技师

这是一组虚构演示数据，不是默认税率或薪酬政策。样板使用 USD、税与折扣均为 0、每项一位技师，提成为服务净额 50%，小费按服务金额分摊。正式店铺必须使用自身配置。

以按摩样板为例：Lisa 预约 14:00，肩颈护理 30 分钟 $40（Amy / 1 号床），全身放松 60 分钟 $80（Ben / 2 号床），顺序执行。

| 步骤 | 操作 | 确定结果 |
| --- | --- | --- |
| F01-1 | 确认到店 | 卡片转候客，原预约身份和项目保留 |
| F01-2 | 查看/调整单项技师与工位 | 只改选中项；后端验证技能和资源；样板只提供预设可用人位 |
| F01-3 | 开始肩颈护理 | 第 1 项进行中，第 2 项待开始；只占用第 1 项位置 |
| F01-4 | 第 1 项增加 15 分钟 / $10 | 第 1 项变为 45 分钟 $50；第 2 项计划改为 14:45–15:45；总服务费 $130。真实实现若有后续冲突须说明并处理，不能静默挪动别人 |
| F01-5 | 完成第 1 项 | 1 号床转待清洁；第 2 项仍可开始；不提前结束整单 |
| F01-6 | 开始并完成第 2 项 | 两项完成，2 号床待清洁，整单进入待收款 |
| F01-7 | 输入小费 $20，现金实收 $160 | 应收 $150，找零 $10；尚未点击确认时只显示预览 |
| F01-8a | 按找零 $10 确认 | 服务费 $130、小费 $20、净现金流入 $150；提成 Amy $25 / Ben $40；小费 Amy $7.69 / Ben $12.31 |
| F01-8b | 或勾选“不用找了，转小费” | 小费 $30、应收 $160、找零 $0；提成仍 $25 / $40；小费 Amy $11.54 / Ben $18.46 |
| F01-9 | 查看记录并完成清洁 | 已付款结果保留；清洁是独立操作，不能因收款自动清空 |

小费使用最大余数法保证分配合计精确到分。样板同时提供美甲、足疗、美睫、头疗、美发和综合店的项目/工位用语，用同一流程验证适配，不宣称覆盖这些行业的全部业务。

第二组重点场景 F02 为“服务款先收、小费后收”：先收 $120 服务款再开始两项，完工后只收小费。先收全款 F03 也保留。已经收款后的追加项目及退款有更复杂账务，正式实现按 GF-10/GF-18 验收，不以样板中禁止编辑来缩减产品需求。

## 6. 本地验收与替换标准

本地实现完成必须同时具备：

- GF-01–GF-36 有实际入口、后端实现与证据链接；外部等待项单列，不用模拟成功冒充真实完成。
- 七种行业预设均能从空数据开店；A01–A18 按适用行业展开并有实际结果。
- 核心账务、租户隔离、资源冲突与幂等在独立测试库验证；UI 关键流程在浏览器验证。
- 接口失败、重复点击、刷新恢复有可复现场景；错误能指导下一步。
- 中英文完整主流程；当前各端已支持语言不退化；窄屏与触屏有单独证据。
- 新旧同一组业务输入的金额、资源和权限结果可比较。差异需记录为有意变更或缺陷。
- 新版一条启动入口、固定演示账号与可重复测试数据；不要求用户手工补缺失表或状态。

替换旧版还需要备份、保留标识的迁移映射、迁移前后数量/金额核对及回退演练。这些不在交互样板中伪造完成。

## 7. 实施顺序与完成记录

执行顺序：需求/样板 → 统一接口及状态定义 → 后端业务与集成测试 → 各端界面与真实接入 → 全行业端到端验收 → 新旧对照。每个阶段都可以自行细分任务，不需用户逐页决定。

后端先提供稳定契约、测试数据和允许动作；前端阶段也承担联调发现的后端问题。若使用两个 Goal，第二条的终点必须包含全流程联调，不只是“页面生成完”。

本轮已完成：GF-01–GF-36 规格、统一状态与动作规则、F01 精确示例、可交互样板。样板使用内存数据，不调用业务 API，不保存真实预约或付款；其验证不能代替后端或产品验收。

## 8. 本轮样板验证记录

使用本地 Chromium 无头浏览器实际点击，结果通过：

- 7 种行业样板 × 3 种收款方式，共 21 条流程从预约推进到完成。
- 修改待开始项目的技师后回显；增加 15 分钟后服务费从 $120 变 $130，第二项计划时间变为 14:45–15:45。
- 完成首项后对应工位可单独清洁，其余项目仍能继续。
- 应收 $150 时输入 $100，确认按钮禁用；输入 $160 得到 $10 找零；勾选找零转小费后，小费为 $30、总收款 $160。
- 收款凭证核对：提成 $25 / $40，小费 $11.54 / $18.46，合计准确。
- 360、736、1024 像素，亮色/暗色共 6 种布局检查未发现页面横向溢出；目视检查 736 亮色和 360 暗色截图。
- 浏览器未捕获到脚本运行错误。

验证边界：样板只模拟单客顺序履约、预设人位与内存账务；未验证真实权限、资源并发、网络失败、退款、数据库持久化或外部服务。已收服务款后的加项与修改暂不在样板开放，正式产品需求 GF-10/GF-18 仍保留。

## 9. 前端视觉标准与工作台方向

用户明确否决第一版样板的视觉效果，要求高端风格，至少优于现有前端。第 8 节的流程检查仍有效，但第一版样板不作为视觉基线；视觉质量是替换验收的独立条件。

用户最新决定：现有项目的 UI 风格不错，自定义 Kanban 和日程应保留优点。正式基线改为现有浅色/青绿色界面、卡片与抽屉；重点统一组件状态、排版、间距、层级与错误恢复，并修复实际缺陷。保留当前 Kanban 与日程的产品交互，拆解内部实现，不默认换通用日历库。此前暖白/深色窄导航的工作台样板仅作为历史探索，不作为重构目标。

正式前端验收要求：

- 预约、收银、客户、员工、库存、设置等主页面共享排版、颜色、表格、表单、弹层和状态组件，不能只有首页精修。
- 与现有版本使用相同业务场景截图对照，检查信息层级、阅读负担、主操作位置和异常状态；不以主观百分比宣称提升。
