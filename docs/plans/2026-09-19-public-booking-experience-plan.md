# 对外预约体验全面审查与改进计划

日期：2026-09-19
状态：实施与本地隔离验收完成；交付范围、测试证据和未提供能力见[验收记录](2026-09-19-public-booking-experience-review.md)。未发布生产，未向真实收件人发送测试通知。
适用：供下一轮 Goal 模式 AI 接手执行。

## 1. 用户目标与执行方式

全面审查并改进当前项目的对外预约体验，对标 Square Appointments、Fresha。范围包括店铺展示页、分步骤预约、单人/多人预约、预约管理，以及顾客和店家两端的短信与 Email。

用户明确要求：

- 一个展示页包含店铺基本信息及所有项目。
- 预约页分步骤完成：单人/多人、添加项目、选择服务人员、选择时间、输入联系方式。
- 顾客打开预约详情网址后可以修改、取消预约。
- 同时审查顾客及店家收到的短信和 Email。

先检查现有实现，复用已有能力，不要直接推倒重做。先产出问题清单、页面方案和数据/API 改动计划，再分阶段实施。方案是执行过程中的可审查产物，不因常规设计选择反复暂停；业务语义无法从代码和上下文确定时，记录问题并推进独立工作。

接手时读取适用的 AGENTS.md 和技能要求，检查工作区已有改动，保留其他任务的工作。不要将本计划的初步观察当作已经复现的缺陷。默认使用测试门店和测试收件地址进行验证，不向真实顾客或店家发送测试消息。生产发布不属于这份计划默认授权的操作。

## 2. 目标页面结构

完整链路：

**店铺展示页 → 选择单人/多人 → 添加项目 → 选择服务人员 → 选择时间 → 填写联系方式 → 确认预约 → 预约成功 → 预约详情/修改/取消**

店铺展示页和分步骤预约页明确区分，同时保持一致的店铺品牌和视觉风格。优先保证手机端体验，再适配桌面端。

## 3. 店铺展示页

### 3.1 店铺基本信息

- 店名、Logo、封面及店铺照片。
- 店铺简介、地址、地图导航、联系电话。
- 营业时间、当天营业状态、店铺时区。
- 必要的停车、交通和到店说明。
- 预约、改期、取消政策。
- 明确且容易找到的“开始预约”按钮。
- 信息缺失时自然隐藏，不展示虚假内容或大片空白。

### 3.2 全部项目

- 展示所有对外公开项目，明确哪些可在线预约，不暴露内部或隐藏项目。
- 分类导航、分类排序；项目较多时支持搜索。
- 项目卡片包含图片、名称、简短介绍、时长、价格、详情入口和添加按钮。
- 支持无图项目，保持卡片布局完整。
- 完整详情包含服务内容、适用说明、注意事项和可选附加项目。
- 套餐明确显示包含项目、总时长和价格。
- 准确表达固定价格、“起价”和价格区间；没有对应业务能力时不要假造。
- 从展示页添加项目后，进入预约流程时保留选择；多人模式明确选择归属。

### 3.3 后台维护能力

核查并补齐店家维护店铺照片、简介、项目图片、详情、分类、排序和在线可预约状态的入口。图片需要合理尺寸、压缩、加载占位和失败回退。

## 4. 分步骤预约页

明确显示进度，返回上一步保留有效选择。改变人数、项目或服务人员后，重新校验受影响的时间及价格。

| 步骤 | 必须实现的体验 |
| --- | --- |
| 1. 单人/多人 | 选择预约人数；说明多人如何安排；人数受门店容量和预约规则限制 |
| 2. 添加项目 | 每位顾客可添加、移除多个项目及附加项目；清楚显示项目归属、时长和费用 |
| 3. 服务人员 | 每个项目选择符合资质的服务人员，或“不指定”；展示姓名、头像及必要介绍 |
| 4. 时间 | 只显示满足所有项目、人员和资源约束的时间；清楚展示日期、星期和时区 |
| 5. 联系方式 | 联系人姓名、手机、Email、备注；合理校验，支持国际号码；区分预约通知与营销订阅 |
| 6. 确认预约 | 展示每位顾客的项目、人员、时间、总时长、费用及政策；确认后提交 |
| 7. 成功页 | 展示预约编号、完整摘要、管理预约入口、添加日历、导航和联系店铺 |

### 4.1 单人多项目

- 明确项目执行顺序和每项开始、结束时间。
- 正确处理服务时长、间隔时间及员工切换。
- 不允许仅按第一个项目的可用时间创建整单预约。
- 区分累计服务时长与实际到店停留时长，避免有间隔时误导顾客。

### 4.2 多人预约

- 可以用“顾客 1、顾客 2”等方式区分，不强迫每人填写完整联系方式。
- 支持每人选择不同项目和服务人员。
- 明确支持的安排方式：同时开始，或允许错开时间。
- 如果现有排程不能保证同时开始，必须如实展示每人的时间，不能误导为同时服务。
- 同一员工或房间不能在同一时间被重复占用。
- 展示整组预约摘要、每人明细和总费用。
- 整组提交应保持一致性，避免只成功预约其中部分人却显示全部成功。
- 审查现有 partySize、预约项和分组模型是否真正表达每人多项目，不把人数乘数当作完整多人排程。

### 4.3 边界体验

- 满约、休息日、员工不可用、项目下架、价格更新。
- 时间刚被其他人抢走、网络断开、重复点击提交。
- 跨月、跨年、夏令时和跨时区访问。
- 无可约时间时给出下一可约日期或清晰替代操作。
- 刷新与返回时尽可能恢复填写内容，但必须重新校验可用时间，并避免不必要地持久化敏感信息。

## 5. 预约详情网址与自助管理

顾客通过成功页、短信或 Email 中的专属网址，打开对应预约详情。

### 5.1 预约详情

- 店铺信息、预约状态、编号。
- 每位顾客的项目、服务人员、日期、时间、时长及费用。
- 地址导航、联系电话、适用政策。
- 清楚展示可以进行哪些修改，以及不能修改的原因。

### 5.2 修改预约

- 支持改期。
- 审查并规划修改项目、附加项目、服务人员、人数及联系信息。
- 可修改范围必须由后台规则明确控制；不支持的情况提供联系店铺入口，并在交付报告中说明限制。
- 修改前展示变更摘要，包括原时间与新时间、原费用与新费用。
- 重新计算价格、时长、人员和容量；明确历史价格快照与新报价的适用规则。
- 修改失败时保留原预约；成功后同步详情、后台日历和双方通知。
- 多人预约需明确“修改整组”和“修改某位顾客”的范围，避免意外影响其他人。
- 涉及联系人变更时检查验证与通知去向，不允许通过弱验证接管预约。

### 5.3 删除/取消预约

- 面向顾客使用“取消预约”，底层保留业务记录，不直接物理删除。
- 显示取消政策并二次确认。
- 多人预约明确取消整组或其中一人；根据实际支持能力提供对应操作。
- 取消后释放资源、停止旧提醒、同步后台并通知双方。
- 已取消详情仍可查看，提供再次预约入口。

### 5.4 链接与验证

- 专属管理链接不可猜测，不暴露其他顾客资料。
- 检查令牌有效期、验证方式、错误次数限制和跨店隔离。
- 无效、过期、已取消及已完成预约都有明确页面状态。
- 管理页避免被搜索引擎收录，避免敏感令牌泄露到日志或外部链接。
- 后端必须独立执行身份、状态、截止时间及资源校验，不能仅依赖前端隐藏按钮。

## 6. 顾客、店家和服务人员通知

先建立通知矩阵，逐项确认触发条件、收件人、渠道、模板、跳转地址和发送状态。

| 事件 | 顾客通知 | 店家/负责人员通知 |
| --- | --- | --- |
| 新预约成功或待确认 | 当前状态、预约摘要、管理入口 | 新预约明细及处理入口 |
| 店家确认或拒绝 | 明确结果和下一步 | 按业务需要同步相关人员 |
| 顾客修改预约 | 修改后的详情及变更摘要 | 谁修改、修改了什么 |
| 店家修改预约 | 原信息与新信息、必要说明 | 同步负责人员 |
| 顾客取消预约 | 取消结果、再次预约入口 | 取消范围及释放的时间 |
| 店家取消预约 | 取消结果、原因及联系入口 | 同步相关人员 |
| 到店前提醒 | 正确时间、地址、准备事项及管理入口 | 按门店设置决定是否提醒 |

未实现的事件状态不能只添加模板，需要先明确业务是否支持。按门店通知设置及渠道可用性执行，不因上线而擅自为存量门店开启收费通知。

### 6.1 顾客短信

- 简洁显示店名、日期时间、核心项目和管理链接。
- 多人、多项目时合理概括，不发送过长且难读的内容。
- 改期明确新时间；取消不能继续使用确认语气。
- 检查中文、特殊字符、长链接和短信分段。
- 通知内容以预约实际状态为准。

### 6.2 顾客 Email

- 统一品牌样式，手机端可读。
- 清楚展示项目明细、服务人员、时间、价格、地址和政策。
- “查看/管理预约”为主要操作。
- 支持纯文本版本，图片不加载时仍可理解。
- 检查主题、发件人名称、回复地址及所有链接。

### 6.3 店家及服务人员短信/Email

- 快速看清顾客、人数、项目、人员、时间、备注和变更内容。
- 操作链接进入正确门店的后台预约详情，并遵循登录权限。
- 区分店主、门店和负责人员，防止发错店或向无关员工发送。
- 保留现有“顾客邮件原样抄送”的核对用途，审查其与独立业务通知的重复情况。
- 顾客未填写 Email 时，也要检查店家独立通知是否正常触发。

### 6.4 通知可靠性

- 检查重复提交、事件重试和重复回调是否导致重复发送。
- 连续多次修改预约，每次有效变更均应正常通知。
- 改期或取消后，旧提醒必须失效。
- 区分待发送、已发送、已送达和发送失败；供应商不提供送达证据时不要宣称已送达。
- 成功页不能在未发送时声称“短信已经发送”。
- 发送失败不能让已成功预约被误判为失败并诱发重复预约。
- 提供可追踪的发送记录和必要的重试机制。
- 检查事务提交与消息入队的一致性，避免预约回滚后仍发送成功通知。

## 8. 执行顺序与交付物

### 阶段 1：审查与方案

交付现状流程图、问题清单、竞品参考、页面结构、通知矩阵、数据/API 差异及实施顺序。问题标记为“已复现”“代码风险”或“待验证”，附位置、影响与证据。

### 阶段 2：页面设计

交付展示页、各预约步骤、单人/多人摘要、预约管理页、短信和邮件预览。覆盖正常、加载、空数据、失败和不可修改状态。

### 阶段 3：预约核心实现

先完成必要的数据和排程能力，再接入页面。重点保证多项目、多人、并发占用、修改与取消的一致性。需要数据库迁移时说明存量数据兼容、默认值及回退方式。

### 阶段 4：通知实现

统一事件与模板，完成顾客、店家和负责人员通知，以及提醒更新、发送记录和去重。

### 阶段 5：验收

使用测试门店和测试收件地址完成真实页面流程验证，交付截图、模板样例、测试结果和剩余限制。采用适合改动范围的单元、集成和端到端测试，重点验证业务边界与并发一致性。

建议在本目录持续维护审查报告和完成情况。不得仅凭代码编译成功宣称全链路完成；无法验证的外部渠道应明确记录。

## 9. 优先级

- **P0 正确性**：重复预约、时间/价格错误、改期取消不同步、通知漏发或错发、管理链接权限问题。
- **P1 核心体验**：店铺信息、图片与详情、分类、手机预约流程、单人/多人及多项目、顾客管理页、双方通知模板。
- **P2 体验完善**：多语言、无障碍、加载速度、日历与导航、空状态和错误提示。

P0 优先于视觉完善，但不能因修完 P0 就将全部目标视为完成。
