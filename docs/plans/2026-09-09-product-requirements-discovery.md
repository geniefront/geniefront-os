# GenieFront 本地新版：需求扫描与产品底稿

日期：2026-09-09。扫描基线：`807b773`；扫描开始时工作树干净。

这是一份从仓库反推的需求草案，不是重写实施授权，也不是上线审计。用户已明确：各行业都重要；先在本地比较新版，满意后再考虑替换现有版本。本轮只增加本文档，没有修改业务实现、环境配置或数据库。

## 1. 最重要的结论

项目已有大量明确的业务需求，缺少的是一份及时更新、能核对实现与验收的产品说明。早期调研、已定决策、代码注释、实施计划和追加交接混在一起，容易把旧限制当成现行规则，也容易把“某次修复完成”读成“整套系统已验收”。

建议新版的产品定义：

> 一套面向美甲、美睫、按摩、足疗、头疗及综合 SPA 等门店的多语言营业系统。前台单台电脑可以完成从预约、到店、服务到结账、分配收入和日结的全过程；技师手机、自助 iPad、顾客预约页与 AI 在同一业务规则上协作。

这保留全部行业，不需要现在选掉任何一种。实现共用业务模型，验收必须分别覆盖行业差异。

## 3. 从仓库提取的需求基线

“保留”指纳入新版需求清单，不表示所有路径当前已通过验收。实现细节不必照搬。

| 领域 | 现有需求与实现线索 | 新版应达到的业务结果 |
| --- | --- | --- |
| 开店 | 七步向导、行业服务预设、服务端 readiness、功能开关 | 店主知道还缺什么；保存后刷新不丢；电话等可选功能不阻断开店 |
| 服务目录 | 服务、时长、价格、加项、技能、所需技师、资源、组合套餐 | 一个服务定义能被前台、预约页、技师与计价共同使用 |
| 员工 | 岗位、职级、技能、权限、可接单、轮牌参与、排班、打卡 | 老板兼技师、前台代操作都成立；这些概念不混为一个“员工等级” |
| 预约 | 前台代订、公开预约、改期取消、多个项目、资源冲突 | 日期、技师、工位与通知保持一致；同号多人先明确对应客户 |
| 到店与候客 | 预约签到、匿名散客、排队、点钟、自动建议与人工派单 | 不填不必要资料也能接待客人；前台明确知道下一步 |
| 项目履约 | 一客多项、多技师、换工位、开始完成、加钟加项、回退 | 每项独立推进；无需员工手机也能完成整单 |
| 房间与工位 | 单人/多人资源、容量、实际占用、清洁、停用 | 完成一项只释放相应位置；服务中、预约占用、清洁分清 |
| 轮牌 | 整轮/半轮、点钟规则、休息、手动排序、事件依据 | 每次接客如何影响顺序说得清，实际记账与页面展示一致 |
| 收银 | 三种收款时机、混合支付、组单、找零转小费、折扣、退款 | 同一单从看板和收银入口得到同一结果，重试不重复记账 |
| 收入与日结 | 提成、小费、现金发放、营业日报表、封账与重开 | 工单、退款、收入和日结可逐项对上，金额使用整数分 |
| 客户与健康表 | 客户档案、共用手机号、历史表单、签名、版本与访问控制 | 找对人、看对版本；关闭新填表不破坏历史记录 |
| 营销资产 | 礼品卡、次卡、优惠券、积分、组合套餐 | 各自余额/次数/优惠语义分开；使用、退款、作废可以追溯 |
| 顾客入口 | 托管预约、自助管理、公开填表、iPad 配对签到 | 手机或 iPad 操作有明确结果，最终进入同一门店营业流程 |
| AI 与通信 | 拍照导入、副驾、电话、通知、沟通记录、评价 | 区分建议、已执行、失败和待人工处理；供应商故障可识别 |
| 平台商业化 | Stripe、订阅码、额度包、开店、到期、运营权限 | 店主与平台操作员权限分开；每店计费事实来源明确 |
| 建站服务 | 品牌资料提交、修改意见、进度、预览、上线申请 | 按现有“建站服务工单”保留，不把它误解成已具备完整可视化建站器 |
| 基础能力 | 多租户、多店、多角色、多语言、营业日、审计、幂等 | 切店不串数据，跨午夜不算错营业日，操作失败能恢复 |

主要依据：`apps/web/src/App.tsx`、`apps/web/src/components/Layout.tsx`、`packages/contracts/src/commands/`、`packages/db/src/schema/`，以及本文第 9 节来源。

## 4. 需要消除的需求漂移

### 4.1 AI 电话已经不止“只能新建预约”

早期 README 强调 AI 必须经人确认；路线图 §A 第 6 条更新为电话可直接预约、不能改删。但是路线图后续批次与当前 `apps/api/src/telnyx/routes.ts` 又增加了改期、取消工具及门店可配置闸门，`ai_change.enabled` 默认 false。

新版基线应分开定义：交互副驾的人工确认；电话直接预约；电话改期取消在开关及条件允许时执行，否则留前台请求。不能把其中任意一句旧原则推广到所有 AI。具体通知成功与供应商可用性仍需集成验证。

### 4.2 计费从 Stripe 扩展为每店一个计费来源

旧审计说明“Stripe 是付费状态唯一来源”。9 月 9 日提交已经加入订阅码、运营签发/改期、门店兑换及到期处理。现行入口是 `apps/api/src/handlers/license.ts`，不是计划早期写的 `billing/license.ts`。

新版应继承 Stripe / license 的互斥与切换规则，并把“顾客向门店付款的记录”与“门店购买 GenieFront 服务的计费”分开。真实迁移、退款及切换效果不能只凭文档宣布通过。

### 4.3 当前开店是七步，且有资源门槛

`features/setup/flow.ts` 和 `setupReadiness` 已包含门店、员工基础、房间、目录、员工排班、功能、开店检查。新店至少一个有效房间/资源的门槛在近期实现记录里已明确。

所有行业都要支持，因此新版可以对美甲叫“工位”、对按摩叫“房间/床位”，底层统一资源。是否进一步允许完全无资源模式属于产品变更，不能偷偷在重写时删掉现有约束。

### 4.4 “套餐”至少有两种完全不同的意思

组合套餐是一次消费中的多个项目组合；次卡是未来多次消费的权益。近期实现增加了组合套餐报价、子项、折扣分摊、前台与公开预约入口。不能用同一个含糊的“套餐”选项替代两套规则，也不能把报告前半部分的“前端待做”当成最新状态，后半部分已有追加实现。

### 4.5 看板旧缺陷清单不能直接当成当前缺陷清单

`docs/30-QUEUE-BOARD-REWORK-PLAN.md` 开头仍列多项阻断问题，但后续日志已经记录修复。当前代码有 `queueNextAction()`、逐项动作、分阶段收款和回退相关实现。

这些历史问题最适合转成回归场景；本次未复现，不宣称它们现在仍存在。值得继承的经验是：预约、工单、项目、付款、轮牌和资源有不同生命周期，必须明确各自事实来源，再统一投影到界面。

### 4.6 “有 AI 名称”不等于调用了模型

当前 Queue 引用 `features/forms/mockData.ts` 的 `generateAiHealthSummary()`，该函数按字段和阈值生成固定文本。本次仅确认这一调用路径，不能因此认定全部健康表功能都是模拟的。

新版需明确标识规则提示与真实模型生成的摘要，展示依据和来源；不凭缺少勾选项自动推断健康结论。这是输出准确性需求，不是本次对医疗规则的专业评估。

## 5. 多行业怎么同时支持

统一的业务骨架：客户 → 预约/现场到店 → 一个或多个服务项目 → 技师与资源 → 履约 → 收款 → 收入与日结。

行业差异放到服务和门店配置中，避免只靠行业名称硬编码整条流程：

| 验收画像 | 必须单独覆盖的差异 |
| --- | --- |
| 美甲/美足 | 技师技能、临时加项、工位切换、同客多项目、按规则允许的技师并发 |
| 美睫/美眉 | 长时段预约、指定技师、补做项目、相关表单与历史信息 |
| 按摩/SPA | 房间/床位容量、单次多个项目、指定技师、服务单、清洁、分阶段收款 |
| 足疗 | 大厅多人容量、多人同时在场、部分位置释放与清洁、轮牌、组单付款 |
| 头疗/综合店 | 项目组合、技能与资源要求不同、跨项目换技师、整体与单项改期 |

仓库另有 hair 服务预设，应在完整清单中保留；具体首发深度依现有实际功能与场景核对。各行业都在范围内，不代表每种店都必须开启所有配置。

## 6. 建议的新产品结构（设计提案，不是现状描述）

店内工作台按日常任务组织为六组：

1. **今日营业**：谁在等、谁在做、做到几点、哪些位置可用、谁该付款；日程/候客/资源是同一批业务的不同视图。
2. **预约与客户**：预约建立和变更、客户历史、表单和沟通记录。
3. **订单与收银**：单据、分阶段收款、合并付款、退款、礼品卡/次卡核销。
4. **员工与收入**：人员、技能、排班、打卡、轮牌规则、提成与小费发放。
5. **经营与增长**：日结、报表、优惠权益、评价、消息、建站服务。
6. **门店设置**：目录、资源、规则、权限、AI、设备、通知和订阅。

技师入口保持任务、收入、个人设置简洁；顾客预约与 iPad 保持独立使用界面；平台运营保留独立权限与界面。合并导航不等于取消功能或把不同角色塞进同一个页面。

## 7. 以场景定义“完成”，而不是只按页面数

下面是验收骨架，不是已通过清单。实施前要为每条补充前置数据、操作步骤和精确预期，并映射已有测试。

| 编号 | 场景 | 结果要求 |
| --- | --- | --- |
| A01 | 各行业从空店完成配置，刷新后继续 | 目录、员工、资源、开关真实保存；缺项明确；能进入营业 |
| A02 | 没有技师手机和 iPad，一位前台接待散客 | 从建单到日结全部可操作，没有其他设备才能完成的步骤 |
| A03 | 预约客同号不同人，签到后改时间/技师 | 人选明确；日程、候客、工单展示一致 |
| A04 | 一位客人两个项目、不同技师和工位 | 每项能开始、完成和调整，最终能正确结账 |
| A05 | 足疗大厅多人服务，其中一人先完成 | 仅相应位置释放/清洁，其余服务保持进行中 |
| A06 | 两个前台同时抢最后一个资源位置 | 物理容量不被突破，失败一方收到可操作的反馈 |
| A07 | 点钟、休息、手调、缺少当天轮牌参与行 | 展示顺序和实际消耗一致，每次变更有依据 |
| A08 | 三种收款时机分别从看板和收银进入 | 合法下一步一致，服务款/小费不重复或遗漏 |
| A09 | 组合套餐加项、拆分、部分退款 | 工单、优惠、退款、提成与报表能逐项对上 |
| A10 | 多客合并付、现金刷卡混合、找零转小费 | 每单合计、支付方式合计、小费分配同时正确 |
| A11 | 礼品卡/次卡使用后退款或作废 | 权益变动可追溯，重试不重复扣除或返还 |
| A12 | 跨午夜、不同门店时区、封账重开 | 营业日一致；历史记录保留，差额可解释 |
| A13 | 多店切换、前台/技师/老板/运营访问 | 不串店，脱敏和写权限在服务端有效 |
| A14 | 公开预约、自助管理、iPad 签到填表 | 状态进入同一营业链；链接、开关、版本行为一致 |
| A15 | AI 预约、改期取消开关关闭/开启、供应商失败 | 已执行与待人工处理明确；没有成功写入就不声称预约成功 |
| A16 | Stripe/订阅码续期、到期、切换和事件重放 | 每店来源明确，其他门店不受影响，额度不重复发放 |
| A17 | 中文/英文完整流程，其他已支持语言与触屏检查 | 字段、按钮、错误与布局可用，主操作不依赖拖拽或悬停 |
| A18 | 请求超时、重复点击、刷新与断网恢复 | 不假成功、不重复写；只读与不可执行状态明确 |

本地模拟可证明内部编排与失败处理，不能代替真实邮件投递、电话通话、支付供应商与真实设备验收。

## 8. 用户现在不需要补一整份 PRD

可以暂用以下工作假设继续梳理，均不是不可更改的决定：

- 各行业都保留，以当前已实现能力为功能基线；早期调研中的每个愿望不自动加入重写范围。
- 允许重新组织页面和技术实现，保留业务结果、历史数据含义及已接受规则。
- “本地替代版”指本地可运行、真实数据库可持久化、完整流程可验收；外部服务哪些模拟、哪些真测，要逐项写清。
- 新版与旧版并行运行，替换时另做迁移与回退验证；不把新库测试通过等同于旧数据迁移成功。
- 现有测试和历史故障场景作为资产继承；不能为了通过验收而删掉不方便实现的行为。

建议接下来的具体产物是正式需求矩阵：每项有稳定编号、现状证据、目标行为、行业适用范围、验收场景、待确认点。然后为最复杂的“一客多项目 + 多资源 + 分阶段收款”画出可操作的流程，用具体示例让用户评判。这个例子验证共用模型，不代表其他行业或功能被删掉。

只有影响业务结果的分歧需要用户裁决，例如某种退款是否要追回已发收入、某类 AI 操作是否允许自动执行；页面拆分、组件组织等实现决定由执行方处理。优先核对既有决策，避免重复询问已经明确的内容。

在功能边界与验收矩阵完成前，不把粗估的“3–7 天”当作已经验证的交付承诺。
