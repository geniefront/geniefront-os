## 用户目标与交付范围

用户已明确选择：**会员是月费／年费、自动续费和周期权益的付费会员**。本计划不以积分设置页替代付费会员。Package 指购买后跨多次消费使用的次卡；沿用现有 `package_templates` 和 `customer_packages`，与一次消费的 `service_bundles` 分开。

目标交付为可运行的完整实现、数据库迁移、隔离测试、浏览器验收和 Stripe 测试模式实测。生产发布、真实扣款及给真实顾客发送测试消息不属于本计划的默认执行范围。外部账号或凭据不足时继续完成独立工作，准确保留未验证项，不能用 mock 通过代替外部闭环完成。

优先调查并修复以下一致性缺口：

1. 当前营销页发礼品卡直接调用 `giftcard.issue`，不能据此认定已收款。付费售卡和有权限的赠送必须成为不同的业务动作。
2. 次卡发行在 `customer_credit_ledger.amount_cents` 中写入售价，而结账核销路径会写入扣减次数。需要统一单位与历史兼容策略，禁止对不同单位直接求和。
3. 次卡结账读取模板中的适用项目，并从发行账本推导售价。购买时必须锁定权益、价格、有效期与提成口径，模板更新不能改变已售资产。
4. 部分次卡发行／核销命令的幂等键仍是 optional；涉及收款或资产变更的入口和兼容别名都必须防重。
5. 现有退款路径对部分预付资产场景限制整单退款。新功能必须明示支持范围并实现本计划所需的按原支付分配退款，不能绕过旧保护直接改余额。
6. `identity.memberships` 是员工／组织身份；顾客会员必须使用不同名称、权限和数据模型。
7. 现有 E2E 配置未完整覆盖 `apps/booking`。本任务必须把新增顾客购买与定金流程纳入自动和浏览器验收。

## 首版业务规则

这些是为执行确定的默认产品规则。除用户后续明确调整外，直接按此落地，避免实施期间反复停下来询问常规选择。

### 定金

- 门店配置固定金额或服务金额百分比，两者互斥；默认沿用现有固定金额设置。按服务折后金额计算，金额不超过当前应付服务金额，不含小费，税额由明确的税费配置计算。
- 在线预约启用定金时，先建立受资源容量约束的限时占位，再进入支付。默认占位 15 分钟；支付平台 Session 有效期和本地占位时长必须显式协调，不能假设两者相同。
- 未付款显示“待付定金”；只有确认支付成功且预约成功落地才显示“预约已确认”。支付成功页通过服务端查询状态，webhook 是异步事实来源。
- 支付超时释放占位。付款成功晚于释放时必须重新原子校验并取得容量；取得失败进入退款处理并通知顾客，不能插入超容量预约。
- 前台可记录线下已收定金，注明渠道、操作人、时间与外部参考号；手工记账不能伪装为平台已验证的线上扣款。
- 到店自动带出可用定金，由前台确认抵扣；定金是已付款，不是折扣。同一笔定金不可重复抵扣，剩余部分仍可追溯。
- 默认按门店现有取消截止时间判断：截止前取消全额退未使用定金；截止后和 no-show 进入前台处理，默认不自动罚没。若门店启用保留定金政策，保存顾客购买时看到的政策版本与确认记录。
- 同店改期沿用已付款定金和原政策快照；价格变化只重新计算应收余额。增加应补定金时创建独立补款，不静默再次扣卡。降低后多出的定金显示可退款余额，不自动增加小费。
- 兼容单人、多人、组单、前台与 AI 电话预约。多人收款要有确定的每人分摊；AI 电话预约需付定金时必须说明待付款，并提供支付链接或前台处理，不提前宣称已收款。

### 礼品卡

- 支持固定面额模板、自定义面额、售价与面值不同、购买人和收礼人、留言、电子卡号及二维码。
- 店内销售支持线下收款记录；在线购买使用门店收款账户。支付确认与发卡建立唯一关联，付款失败不发有效卡。
- 保留既有门店／组织范围；默认新卡仅限发行门店，同组织跨店使用需显式配置和对应门店对账。
- 默认无到期时间；复用现有余额、混合支付和提成配置，补齐领取、查询、挂失停用／补发和发信重试。补发使旧凭证失效，余额及历史不重复。
- “消费退款退回卡”和“撤销购卡原路退钱”分开。购卡退款上限按未消费面值对应的实付比例计算，赠送面值不直接兑成现金；已退款和已消费部分均不可再退。
- 礼品卡默认不购买另一张卡、次卡或会员，不支付小费；限定用于门店服务及既有明确允许的消费项目。
- 卡号和顾客资产查询要限流、最小化返回信息；完整卡号不进入日志、分析事件或审计。查询余额不自动授予退款或改持有人权限。

### Package 次卡

- 支持模板、限定项目、次数、售价、有效期、门店范围、购买客户及在线售卖开关。默认实名使用，不支持转让／多人共享。
- 首版支持有限次数，以及现有已支持的有限有效期 unlimited 方案。新建 unlimited 必须有期限与明确适用项目；不能用“0 次”推断为已用完。
- 明确两种现有核销语义：一次覆盖一项指定服务，或一次覆盖模板规定的一组服务。模板和购买快照均记录语义，前台结账解释本次扣几次、覆盖哪些项目。
- 次数流水和货币价值分别记录，使用专用权益流水或明确单位字段；不能继续让 `amount_cents` 同时表示分、积分与次数且跨单位汇总。
- 购买完成后发放资产；并发核销不超扣。适用项目、次数、价格、期限和提成快照不随模板变动。
- 按原购买价分摊已用／未用权益，确定性处理余数；有限次卡支持退未用部分。Unlimited 不从次数推算退款额，提供有权限的人工金额退款并限制累计不超过实付，终止或调整剩余有效期。
- 撤销服务核销与撤销次卡购买是两类操作：前者恢复对应权益，后者退购买款并减少未用权益，均能追溯原流水。
- 维持当前 service bundle 与次卡核销的边界：不能对已覆盖的组合套餐子项再抵扣一次。UI 显示原因，不能静默忽略。

### 付费会员

- 支持月付与年付计划，顾客在门店账户下订阅、自动续费。每客户每门店默认最多一份有效会员；同一购买重试不能产生两份订阅。
- 开通页展示本次收费、续费金额与频率、下一次收费日期、权益到期和取消方式，保存顾客明确同意自动续费的版本及时间；前台代开必须由顾客完成付款方式与续费确认。
- 权益包括限定项目每周期 N 次服务及指定项目会员折扣，可组合。首版不新增通用会员储值充值或自动积分升级；已有积分和退款余额功能继续兼容。
- **收费周期和权益周期分开。** 月付每月收费并发放当月权益；年付每年收费，可选年度一次发放或按月发放，默认按月发放。年付成功后创建已付款覆盖期间内的权益计划，后续月度发放不依赖新的 Stripe 年度账单。
- 以订阅生效日为周期锚点，按日历月／年推进，不使用 30 天／365 天代替；月末、闰年、门店时区及 DST 都要有测试。
- 首版权益不结转，未用次数期末失效；在开通前明确显示。会员次数与 Package 次数分开核销，显示来源、有效期、余额。
- 首次发权益和续费发权益必须由已确认的账单支付触发，校验该账单的账户、订阅、业务类型及覆盖期间；不能只凭订阅 `active` 或 Checkout 返回页发放。
- `incomplete`、需再次认证、支付失败／`past_due`、恢复付款、取消到期、已终止等状态有清楚的页面和后端处理。新周期扣款失败不发新权益；已支付周期的有效权益按原有效期保留。
- 默认周期末取消，期末前仍享已付款权益；支持取消撤回。顾客可更新付款方式、查看账单和管理续费；通过受保护入口进入本门店的 Stripe 客户管理页或等价自助页。
- 默认不设免费试用、不做中途自动按比例升降级。换计划从下个收费周期生效；现有周期权益按旧快照履行。
- 店长可立即终止并发起明确金额的退款，展示已用／未用权益及累计退款上限；年付退款应停止后续月度发放。退款与会员终止是显式关联动作，不能假设退款会自动取消 Stripe 订阅。
- 争议／拒付时冻结受影响的未用权益并形成待处理事项，已履约部分保留历史。支付账户失联、断开或停用时停止新销售，既有订阅必须显示后续处理状态，不能假定断开会自动停止续费。

## 支付与数据设计

### 门店收款

首版选择 Stripe Connect 加托管 Checkout；顾客订阅使用 Stripe Billing。默认 direct charges，使交易归属连接的门店账户；账户配置、适用 API 与权限在实施时按最新官方文档核实。门店开户、状态刷新、补充资料、收款可用性和后台查看入口属于交付范围。平台交易抽成默认 0，不自动开启收费产品。

建立服务端的 org/location 与收款账户映射，验证账户能力和 test/live 模式。同组织共享账户只能由明确配置产生，不允许客户端任意传 `stripeAccount`。顾客、Price、Checkout、订阅、退款与事件都必须携带并校验账户上下文。

新增独立的顾客商业支付服务与事件域，复用签名验证、幂等和编排经验，但不要让顾客续费 webhook 进入现有 `billing_accounts` 或 AI 额度命令。顾客付费会员和 GenieFront SaaS 会员的字段、权限、页面文案与报表必须清晰区分。

以下是职责划分，执行者可以调整具体名称，但必须在实现记录说明映射并维持单一事实来源。

| 实体 | 职责 |
| --- | --- |
| 门店收款账户映射 | 账户 ID、模式、能力、状态及位置范围 |
| 商业订单与订单项 | 礼品卡、次卡、会员首次购买／周期账单、定金的购买事实及价格／规则快照 |
| 支付尝试与支付事实 | 线下记录或 Stripe 收款、金额、币种、状态、外部 ID、幂等关联 |

| 预约占位与定金账户 | 占位截止、预约／分组关联、已收、已用、可退及保留金额 |

现有 `payments` 依赖 `ticket_id`，不强造“虚拟服务工单”来承载未履约的售卡和订阅。商业购买与服务工单通过应用／分配记录关联。货币流水、次数流水和积分流水可以共用基础设施，不能共用模糊单位或互相求和。

### 必须守住的一致性

- 每次收款、退款、资产发放和消费都有稳定业务幂等键；所有金额变更命令要求幂等，包括旧命令别名。数据库唯一约束兜底，不能只靠按钮禁用。
- 外部支付调用在数据库事务外执行；数据库中的支付认领、发权益和结算使用可重试状态机。支付成功但写库失败可以回放恢复。
- webhook 验签后按账户和模式定位租户；事件 ID 去重以外，还要按支付／账单／权益周期去重。乱序事件不能使已退款变回可消费。
- 退款提交后先预留或冻结对应可用权益，成功再完成冲销，失败可恢复；并发退款与消费不能同时花掉同一份余额。
- 资产按确定顺序加锁，保持 RLS、受限连接与 `SET LOCAL`。所有业务写操作走命令总线或现有命令内的同一事务，不嵌套独立事务核销。
- 双 API 实例和定时任务通过数据库认领／租约协作；重启、多实例重叠执行和漏跑补偿都不重复发权益，不新增自管 Redis。
- 保留财务历史，只追加冲销。缓存余额可重建；发现不一致生成可审查的修复结果，不能无依据补钱或扣钱。
- 用户确认快照同时记录规则、版本和时间。顾客资产绑定 `customers.id`，禁止只靠手机号自动授予已有余额或权益。

## 统一结账与财务口径

建立服务端唯一的结账报价／分配实现，并让独立 Checkout、Queue 内联收银、组单付款和预约转单都使用它。前端只显示结果和选择；提交时重算并核实快照／版本，价格或权益变化要给出可理解的重确认。

默认处理顺序：锁定项目与组合套餐价格 → 用户选择次卡或会员次数覆盖项目 → 对未覆盖项目应用会员价／折扣 → 计算税费 → 抵扣已付定金 → 应用礼品卡和既有退款余额 → 收取剩余现金／刷卡；小费独立。既有优惠券与会员折扣首版不自动叠加，同一行选择一个适用价格优惠，额外授权折扣沿用现有权限。

同一服务项只能由一份次数权益覆盖；定金和礼品卡属于支付来源，不应再次降低服务收入或技师提成基数。具体税费与提成遵守现有显式配置并保存交易快照，不能为了让尾款正确而随意改税或提成。会员权益的提成按计划显式配置，允许目录价、已分摊实付价或零，不能把年费在每个月重复当成全额提成基数。

会员实付分摊默认规则：年付先按权益周期用最大余额法分摊，每期再按所含次数权益的目录价权重分配到执行单位；累计分摊恰好等于实付，所有余数分配顺序固定。纯折扣会员费单列，不自动分配到服务提成。以上是系统经营计算默认值，保存快照以支持解释、退款和未来规则版本。

服务退款必须沿原分配图恢复卡余额、次数或已付定金，并退款对应的新收款；多次部分退款累计不能超过各来源实付／已核销量。作废、退款和取消本次结账对权益的处理必须明确，不能通过删除原流水实现。

日结和报表至少区分：当天实际收款、当天退款、礼品卡／次卡／会员销售、定金收取、各类资产核销、未履约余额或剩余权益，以及服务营业额、税、小费和技师收入。卖卡收款和后来服务核销不能重复算作现金收入。Stripe gross、手续费、net 和到账批次分别展示；后续银行 payout 不当成又收一笔服务款。会员收款和周期服务履约分开汇总，不将简化的经营报表冒充完整会计收入确认。

## 页面与访问控制

- 店家设置：收款账户连接状态；定金规则；礼品卡、次卡和会员计划管理；清楚显示在线销售是否可用。
- 营销／销售页面：购买、线下收款确认、有权限的赠送、支付状态、退款、卡片送达重试与历史。
- 顾客档案：独立显示礼品卡、次卡、会员状态及本周期权益、定金和既有退款余额；每一项可展开来源流水。
- 预约／日程：待付定金、已付、已抵扣、退款中等状态；发送支付链接、前台线下记录和带原因豁免。
- 收银：显示可用权益和覆盖项目、自动带出定金、剩余应付；空状态、余额不足、过期和范围不符均有人话提示。
- 顾客端 `apps/booking`：购买礼品卡／次卡／会员、付定金、购买结果与安全的订单／会员管理入口；手机优先，延续现有品牌。
- 自助查询使用短效或可撤销的签名／不透明 token，并验证到具体客户和资源；预约管理 token 不自动拥有全部客户资产权限。共享邮箱或手机号不自动合并顾客。
- owner／manager 配置计划及规则；front_desk 销售与核销；退款、赠送、豁免、人工调账使用明确权限和原因；tech 不获得财务管理权限。新增权限同步契约、角色预设与 UI。
- 通知通过现有 Email／站内能力：付款成功、卡片送达、定金待付／退款、会员开通／扣款失败／取消、权益到期。仅授权的业务事件触发；测试使用专用测试收件地址。短信不得成为依赖。
- 沿用六种语言框架，新增文案完整本地化，日期按门店时区、货币按配置；离线仍只读。

## 数据迁移与既有业务兼容

1. 沿用仓库实际的 Drizzle schema 与 `packages/db/sql` 手写迁移机制；接手时确认最新编号和迁移执行器，不另起第二套迁移历史。
2. 新增结构和可空关联先上线兼容代码，再执行可重入 backfill，验证后才加严格约束。提供空库迁移与从当前 schema 升级两种测试。
3. 为历史礼品卡／次卡建立明确的 legacy 来源；没有真实支付凭据时不得伪造 Stripe 支付或可原路退款状态。
4. 次卡旧流水中金额／次数混合必须按事件来源识别；能从购买快照和核销记录推导的做可审计映射，不能确定的进入待核对列表。不得清空旧余额、擅自发新权益或将零价猜成未付款。
5. 历史资产的现有可用性不因新收款功能未启用而消失。历史 unlimited、过期、耗尽后退款、跨店卡及客户合并别名均要覆盖。
6. 开关分别控制新销售／预约收定金／会员订阅；关闭新销售后仍能履行已有资产、查看历史、处理退款及已存在订阅。停止软件任务不能停止外部自动续费，停用流程必须处理这层差异。
7. 回滚以关闭新入口和回退兼容应用为主，保留支付及账本数据；写出失败补偿和 webhook 恢复方式，不以删表或回滚财务流水恢复。
